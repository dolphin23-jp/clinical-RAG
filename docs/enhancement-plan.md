# clinical-RAG の強化案と第1段の設計

状態: **案の整理と設計（2026-10-24）。段階1（会話の保存・数値の突き合わせ・薄い表示）・段階2（症例モード）・段階3（カルテ記載の下書き）は実装済み。第1段のうち T1-1（入力ガード）・T1-2（利用上限。Access の検証は除く）・T1-3（縮退）・T1-5（常時表示とプロンプト）・T1-9（辞書の最初の版）は実装済み**（同日。医師の回答は `docs/clinical-use.md` の 1b）。残りは下の各項の「状態」。前提は `docs/clinical-use.md`（実臨床の参考利用。入力は年代・主要所見・検査値の数値まで、氏名・ID は入れない。最終判断は医師本人）。タグは `[確認]`（コードを読んだ）`[推論]` `[未確認]`。ID（A1 など）は、実装を頼むときの呼び名。

## 0. 読み方

- 実臨床の参考利用では、誤りの害が「誤って覚える」から「誤った数値や見落としが判断に混ざる」に変わる。そのため、安全に関わる案（数値・入力・取りこぼし・失敗時の振る舞い）を上げた
- clinical-modules との連携の案（E）は、Modules が訓練のままなので、優先度を下げた。ただし RAG 単体の価値には関わらない
- 規模は S（半日〜1日）・M（数日）・L（週単位）の目安 `[推論]`

## 1. 現状の見立て

**よくできている点** `[確認]`
- 検索を強制し、引用文は API の `cited_text` で返す。頁は検索結果のメタ情報から引くので、モデルが頁を作れない
- 結果に信頼度の情報が付く（`numeric_critical`、転写者補助、`text_reliability`、`issues`）
- LLM を呼ばない `/api/search` が独立している
- 評価の道具（`eval/run_eval.ts`）と、ベクトル検索の差し込み口（`extraRankings`）がある

**実臨床で使うには足りない点**

## 4. 第1段の設計

各項目は、実装する PR で、同じ変更の中にテストを足す。`cd worker && node --test test/*.test.ts` と `npx tsc --noEmit` と `python3 -m unittest discover -s tests -p 'test_*.py'` を手元で通してから PR にする。

### T1-1 入力ガード（F1）

状態: **実装済み**。設計どおり。氏名と日付は検出しない（医師の決定）。テスト: `worker/test/idguard.test.ts`（共通の例 `tests/vectors/idguard.json` を両実装で）、`worker/test/ask.test.ts`（HTTP の拒否・確認済みの印・履歴）、`tests/e2e/ui_clinical.py`（画面）

- 画面: `web/id-guard.js`（新規。clinical-modules の `web/id-guard.js` の網と同じ。例の入力と期待を、両リポジトリで同じ一覧にそろえる）。送信時に検査し、見つかったら種類の名前を示して「直す／このまま送る」。「このまま送る」は `ack_identifier: true` を付ける
- サーバー: `worker/src/idguard.ts`（同じ網）。`/api/ask` と `/api/search` の入口で、質問と履歴を検査する。見つかって承認の印がなければ 400（`possible_identifier` と種類の名前だけ。検出した文字列は返さない・記録しない）
- 網: 8桁以上の数字、電話番号らしき並び、ID/MRN の後ろの数字、メールアドレス、識別情報の語。氏名と日付は検出しない（`docs/clinical-use.md` の 2.1・2.3。日付の扱いは未決）
- テスト: 網にかかる/かからない一覧（検査値の数字、「eGFR 30」「Cr 1.2」「10-20 mg」、年月日を含む文が誤検出されないこと）。**ブロックしたときは Anthropic の API を呼ばない**（偽の `fetch` が呼ばれないこと）。履歴の中の識別情報も止まること

### T1-2 利用上限と Access の検証（F2）

状態: **日次の上限は実装済み**（`worker/src/usage.ts`。日付は日本時間。値は仮の 100 回）。**Access の JWT の検証は、まだ入れていない**: clinical-modules はサービスバインディング（`env.RAG`）で `/api/search` を呼ぶので、JWT を全ての `/api/*` に求めると、その経路が止まる。どの入口に求めるか（`/api/ask` と閲覧系だけにして `/api/search` を外す、など）を決めてから入れる

- 設定: `DAILY_ASK_LIMIT`（変数。値は医師が決める）。D1 に回数だけのテーブル（日付と回数。質問文は入れない）を置き、`INSERT ... ON CONFLICT DO UPDATE ... RETURNING` で数える。超えたら 429
- Access: `ACCESS_TEAM_DOMAIN` と `ACCESS_AUD` が設定されているとき、`Cf-Access-Jwt-Assertion` を検証する（署名・期限・`aud`。公開鍵は取得して一定時間保持）。設定がなければ、いまのとおり Bearer だけ
- テスト: 上限の前後、日付の切り替わり（日本時間で数えるか UTC かを決める）、期限切れ・別の `aud` の JWT が通らないこと、設定がないときに動作が変わらないこと
- 注意: `Db` 型は読み取りだけ（`all`）なので、書き込みは別の小さな部品にする。`docs/clinical-use.md` の 6 の「書き込みの一覧」の検査に、このテーブルだけを許す

### T1-3 LLM が失敗しても検索は使える（縮退。D1 の一部）

状態: **実装済み**。途中までの回答は残す（医師の決定）。利用者が中止したときは検索し直さない。テスト: `worker/test/ask.test.ts`（API の失敗・ストリームの途中切れ・拒否・往復の上限・中止）、`tests/e2e/ui_clinical.py`

- 回答の生成が失敗したとき（API エラー、ストリームの途中切れ、検索往復の上限、拒否）、質問の内容語で `searchParents` を呼び、`{t: "degraded", reason, items}` を出す。`items` は既存の `sources` と同じ形（書名・章節・頁・フラグ）
- 画面: 「回答の生成に失敗しました。検索で見つかった節です」と出し、各節を既存の根拠シート（全文・頁画像）で開けるようにする。途中まで出た回答は、「途中で切れた回答」の注を付けて残す（捨てるかは医師が決める）
- 理由は短い固定文にし、API キーや上流の詳細を出さない（既存のテストと同じ）
- テスト: 偽の API が 500/529/ネットワーク切断/ストリームの途中切れ/拒否を返したとき、`degraded` が出ること。検索自体も失敗したときは、エラーだけ出すこと

### T1-4 クイック検索画面（D1・D7）

- 画面の上に「検索」の切替を足す。キーワードを打つと `/api/search` を呼び、頁チップ・フラグ・ヒット箇所の抜粋の一覧を出す。タップで根拠シート（`showParent`／`showPage`）を開く。書籍の絞り込みは既存の設定を使う
- `/api/search` の応答に、`snippet`（親の先頭240字）に加えて、**ヒットしたチャンクの前後の抜粋**（`matched_snippet`）を足す。読み取りだけで、既存の使い手（clinical-modules の `worker/books.mjs`）は `snippet` を使わないので影響しない

## 5. 勧めない案

- **LLM の再ランキングや書籍検索を、clinical-modules のエンジンの実行時に挟む**: 同じ入力に同じ出力を返す性質を壊す（Modules の I15）

- **ファインチューニング**: 書籍が著作物で、データも少なく、辞書と評価で足りる範囲 `[推論]`
- **回答・本文のエクスポート機能の拡充**: 書籍の本文は引用に絞る方針と、台帳の「再配布不可」に反する
- **患者の氏名・ID を含む入力を受ける機能**: 決定 3 の外
- **患者固有の用量計算をモデルにさせる**: 算術の誤りが害になる。計算機が要るなら、試験済みの決定論の別の部品として別に決める

- 症例の入力欄は「身体所見・検査・画像・心電図」が1つなので、身体診察と検査所見が分かれた型（A04・A01）では「身体診察」の欄にまとめて入れ、「［身体所見・検査・画像・心電図］」と見出しを付ける（検査所見の欄は条件つきなので出ない）。分けたいときは、症例の欄を分ける（症例モードの変更になる）
- 欄に入るもの（`web/note-assemble.js` の `FILL`。草案の役割は、問題＝問題リスト、評価＝各問題の評価、計画＝初期プラン、基準＝コンサルト・医師コールの基準）:

| 型 | 入力・草案が入る欄 | 入力元のない必須欄（いつも「（未入力）」） |
|---|---|---|
| A04 救急外来初療 | 来院情報＝年代・性別・場面／現病歴＝主訴と経過／患者背景＝既往・内服／初期評価＝バイタル／身体診察＝所見・検査／重症度・第一仮説・鑑別＝先生のアセスメント＋問題＋評価／治療・処置・コンサルト＝計画＋基準 | 帰宅・入院・転院と根拠 |
| A01 外来初診 | 主訴・受診情報＝年代・性別・場面／現病歴／既往／初期安全評価＝バイタル／身体診察＝所見・検査／第一仮説・鑑別＝先生のアセスメント＋問題＋評価／治療・追加検査・説明＝計画／再評価・変更条件＝基準 | 帰宅・紹介・入院・次回診療 |
| A05 病棟入院時 | 入院経路・目的＝年代・性別・場面／入院までの現病歴／既往／入院時状態・検査＝バイタル＋所見・検査／Problem List＝問題／Problem別A/P＝先生のアセスメント＋評価＋計画／再評価予定・退院条件・申し送り＝基準 | Clinical Summary |
| A06 病棟の経過 | 現在の段階＝年代・性別・場面／前回からのイベント＝主訴と経過／所見・検査推移＝バイタル＋所見・検査／Problem別A/P＝先生のアセスメント＋問題＋評価＋計画／翌日確認・再評価・コール条件＝基準 | なし（先生のアセスメントも採用もなければ Problem別A/P、採用がなければ翌日確認・再評価・コール条件は「（未入力）」） |
| A08 退院時サマリ | 入退院日・退院先＝年代・性別・場面／入院理由と現病歴＝主訴と経過／入院時状態＝バイタル＋所見・検査 | 主病名・副病名、Problem別入院後経過、退院時状態・残存課題、外来・在宅の方針、結果待ち・担当者・確認期限。**草案の項目を入れる欄はない** |
| B02 コンサルト依頼 | 症例の簡潔な要約＝年代・性別・場面＋主訴と経過／重要な所見・検査＝バイタル＋所見・検査 | 依頼先・緊急度、依頼の具体的な質問、実施済み評価・治療（計画は入れない）、依頼時刻・相手・回答状況、依頼後の予定・回答確認 |
| B06 申し送り | 現在の状態・主要問題＝年代・性別・場面＋主訴と経過＋先生のアセスメント＋問題／背景・直近の評価＝既往＋バイタル＋所見・検査／次担当者の行動＝計画（「担当・期限は入力していません」を添える）／悪化条件・連絡＝基準 | なし（採用がなければ、次担当者の行動・悪化条件は「（未入力）」） |

- **採用が空のとき**（症例だけ）でも作れる。草案の項目を入れる欄のない型（A08）で採用があるときは、件数を画面に出す
- 記載の本文を医師が画面で書き換える欄は作らない（貼った先のカルテで直す）。必要になったら、症例の入力と同じ識別情報の扱いで足す

### 7.4 段階4: 書籍を参考にした架空症例の作成

- **画面**: 「症例を作る」。入力はテーマ（病名・症候）・場面・難しさ・学ばせたいこと・落とし穴の有無
- **生成**: モデルが書籍を検索し、**典型的な所見・検査値・経過の記述**を根拠に、新しい架空症例を作る。**書籍の症例文は写さない**（著作物と、Modules の「書籍の症例の焼き直しを避ける」）。数値は例示で、**閾値・用量は書かない**（Modules の規則）。「架空症例」の印を常に付ける
- **出力**: 症例の導入文・所見の表（項目・値・根拠の頁）・「見立て」（別の欄。最初は畳む）・落とし穴・教訓。実在の患者を思わせる固有の細部（地名・職業の特定・日付）は入れない（出力にも識別情報の検査をかけ、引っかかれば警告）
- **Modules の訓練症例の下書きの形式**: `drills/*.toml` の `[[case]]` の `id`・`title`・`tags`・`intro`・`key`・`pitfall`・`lesson`・`source`（と `[case.expect]` の鑑別の候補）の形で出す。**`[case.answers]` は、フローの質問ID・選択肢IDに紐づく**（例: `ems_cc = "syncope"`）ため、モデルに直接は書かせない。所見の表を添え、フローの質問への変換は、Modules 側で医師が確認しながら行う（Modules の `scripts/drill.py` が検査する）。変換を助ける道具は、別の段階（Modules の側）
- **使い道**: 作った症例を症例モードの入力に戻せば、「先生自身のアセスメント → 書籍に基づく草案との見比べ → 記載の型」という訓練の循環ができる。Modules の訓練（実患者の情報を入れない）への橋渡しは、医師が下書きを確認してコピーする形のみ
- **テスト**: 書籍の症例文の長い一致が出力にないこと（検索結果の本文との最長一致の長さで検査）、閾値・用量の数値が出力にないこと、識別情報の検査、Modules の下書きの形式の必須欄、画面
- **未決**: 難しさの段階、落とし穴の与え方、Modules への取り込みの手順

### 7.5 順序と、Modules 側の記録

1. 段階2（症例モード）→ 2. 段階3（カルテ記載）→ 3. 段階4（架空症例）。段階2 の草案が、段階3 の記載の中身になる
2. 各段階のPRは、設計（この節）と、テスト、`CLAUDE.md` の守りの部品の追記を含む
3. clinical-modules の `docs/roadmap.md` の決定済みに、1d の決定を記録する（clinical-modules の `CLAUDE.md` の例外の書き方も合わせる）。**Modules 側の運用（訓練のまま）は変えない**
