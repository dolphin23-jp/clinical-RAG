## 0. 読み方

- 実臨床の参考利用では、誤りの害が「誤って覚える」から「誤った数値や見落としが判断に混ざる」に変わる。そのため、安全に関わる案（数値・入力・取りこぼし・失敗時の振る舞い）を上げた
- clinical-modules との連携の案（E）は、Modules が訓練のままなので、優先度を下げた。ただし RAG 単体の価値には関わらない
- 規模は S（半日〜1日）・M（数日）・L（週単位）の目安 `[推論]`

## 1. 現状の見立て

**よくできている点** `[確認]`
- 検索を強制し、引用文は API の `cited_text` で返す。頁は検索結果のメタ情報から引くので、モデルが頁を作れない

- 評価の道具（`eval/run_eval.ts`）と、ベクトル検索の差し込み口（`extraRankings`）がある

## 4. 第1段の設計

各項目は、実装する PR で、同じ変更の中にテストを足す。`cd worker && node --test test/*.test.ts` と `npx tsc --noEmit` と `python3 -m unittest discover -s tests -p 'test_*.py'` を手元で通してから PR にする。

### T1-1 入力ガード（F1）

状態: **実装済み**。設計どおり。氏名と日付は検出しない（医師の決定）。テスト: `worker/test/idguard.test.ts`（共通の例 `tests/vectors/idguard.json` を両実装で）、`worker/test/ask.test.ts`（HTTP の拒否・確認済みの印・履歴）、`tests/e2e/ui_clinical.py`（画面）

- 画面: `web/id-guard.js`（新規。clinical-modules の `web/id-guard.js` の網と同じ。例の入力と期待を、両リポジトリで同じ一覧にそろえる）。送信時に検査し、見つかったら種類の名前を示して「直す／このまま送る」。「このまま送る」は `ack_identifier: true` を付ける
- サーバー: `worker/src/idguard.ts`（同じ網）。`/api/ask` と `/api/search` の入口で、質問と履歴を検査する。見つかって承認の印がなければ 400（`possible_identifier` と種類の名前だけ。検出した文字列は返さない・記録しない）
- 網: 8桁以上の数字、電話番号らしき並び、ID/MRN の後ろの数字、メールアドレス、識別情報の語。氏名と日付は検出しない（`docs/clinical-use.md` の 2.1・2.3。日付の扱いは未決）
- テスト: 網にかかる/かからない一覧（検査値の数字、「eGFR 30」「Cr 1.2」「10-20 mg」、年月日を含む文が誤検出されないこと）。**ブロックしたときは Anthropic の API を呼ばない**（偽の `fetch` が呼ばれないこと）。履歴の中の識別情報も止まること

### T1-2 利用上限と Access の検証（F2）

状態: **日次の上限は実装済み**（`worker/src/usage.ts`。日付は日本時間。値は仮の 100 回。医師の決定でそのまま）。**Access の JWT の検証も実装済み（2026-10-25）**: `worker/src/access.ts`。`ACCESS_TEAM_DOMAIN` と `ACCESS_AUD` の両方があるとき、`/api/health` と `/api/search` 以外のすべての `/api/` に、アプリのトークンに加えて Access の JWT（RS256・期限・発行元・audience）を求める。`/api/search` を外したのは、clinical-modules がサービスバインディング（`env.RAG`）で呼び、Access のトークンを持たないため。片方だけの設定は全部断る（500）。設定がなければ今までどおり。鍵は Cloudflare のチームのアドレスから取り、メモリに持つだけ（保存・ログなし。1分に1回までしか取り直さない）。**設定する値**（Access のアプリの Audience tag とチームのドメイン）は、先生の Cloudflare の画面にだけある。評価の道具を Access の背後の Worker に向けるときは、Access のサービストークンを環境変数 `CF_ACCESS_CLIENT_ID`・`CF_ACCESS_CLIENT_SECRET` で渡す。

- 設定: `DAILY_ASK_LIMIT`（変数。値は医師が決める）。D1 に回数だけのテーブル（日付と回数。質問文は入れない）を置き、`INSERT ... ON CONFLICT DO UPDATE ... RETURNING` で数える。超えたら 429
- Access: `ACCESS_TEAM_DOMAIN` と `ACCESS_AUD` が設定されているとき、`Cf-Access-Jwt-Assertion` を検証する（署名・期限・`aud`。公開鍵は取得して一定時間保持）。設定がなければ、いまのとおり Bearer だけ
- テスト: 上限の前後、日付の切り替わり（日本時間で数えるか UTC かを決める）、期限切れ・別の `aud` の JWT が通らないこと、設定がないときに動作が変わらないこと

## 5. 勧めない案

- **LLM の再ランキングや書籍検索を、clinical-modules のエンジンの実行時に挟む**: 同じ入力に同じ出力を返す性質を壊す（Modules の I15）
- **回答中の用量を、自動で薬剤カードに反映する**: 数値は `verified` のカードだけ、という線を崩す
- **ファインチューニング**: 書籍が著作物で、データも少なく、辞書と評価で足りる範囲 `[推論]`
- **回答・本文のエクスポート機能の拡充**: 書籍の本文は引用に絞る方針と、台帳の「再配布不可」に反する
- **患者の氏名・ID を含む入力を受ける機能**: 決定 3 の外
- **患者固有の用量計算をモデルにさせる**: 算術の誤りが害になる。計算機が要るなら、試験済みの決定論の別の部品として別に決める

- **草案の取り込み**: アセスメントとプランの草案の項目ごとに「採用」を付ける。**採用した項目だけ**が記載のアセスメント・プランの欄に入り、「AI草案」の印が付く（コピーのとき、印を残すか外すかを選べる）。採用しない項目は記載に入らない。草案は、先生が採用するまで記載の本文に入らない（Modules の草案の層と同じ約束）
- **出力**: 画面で確認し、コピーする（実際のカルテに貼るのは先生）。書き出し・印刷・共有は作らない
- **テスト**: 型の取り込み（Modules の型と欄が一致する）、未入力が空欄のまま残ること、日付・ID・氏名の欄が空欄のままであること、採用しない項目が入らないこと、採用の印がコピーに出る/外せること、画面
- **未決**: 最初の型の優先順、欄の文言（先生の施設の記載の慣習に合わせる）、時刻の扱い（入力にある時刻だけを使う）

### 7.4 段階4: 書籍を参考にした架空症例の作成

- **画面**: 「症例を作る」。入力はテーマ（病名・症候）・場面・難しさ・学ばせたいこと・落とし穴の有無
- **生成**: モデルが書籍を検索し、**典型的な所見・検査値・経過の記述**を根拠に、新しい架空症例を作る。**書籍の症例文は写さない**（著作物と、Modules の「書籍の症例の焼き直しを避ける」）。数値は例示で、**閾値・用量は書かない**（Modules の規則）。「架空症例」の印を常に付ける
- **出力**: 症例の導入文・所見の表（項目・値・根拠の頁）・「見立て」（別の欄。最初は畳む）・落とし穴・教訓。実在の患者を思わせる固有の細部（地名・職業の特定・日付）は入れない（出力にも識別情報の検査をかけ、引っかかれば警告）
- **Modules の訓練症例の下書きの形式**: `drills/*.toml` の `[[case]]` の `id`・`title`・`tags`・`intro`・`key`・`pitfall`・`lesson`・`source`（と `[case.expect]` の鑑別の候補）の形で出す。**`[case.answers]` は、フローの質問ID・選択肢IDに紐づく**（例: `ems_cc = "syncope"`）ため、モデルに直接は書かせない。所見の表を添え、フローの質問への変換は、Modules 側で医師が確認しながら行う（Modules の `scripts/drill.py` が検査する）。変換を助ける道具は、別の段階（Modules の側）

- **テスト**: 書籍の症例文の長い一致が出力にないこと（検索結果の本文との最長一致の長さで検査）、閾値・用量の数値が出力にないこと、識別情報の検査、Modules の下書きの形式の必須欄、画面
- **未決**: 難しさの段階、落とし穴の与え方、Modules への取り込みの手順

### 8.1 いまの限界

- 症例は、1回の診察の事実を入れる、平らな7欄（年齢・性別・場面・主訴と経過・バイタル・所見・既往）と、任意の自分のアセスメント `[確認]`

- **診察をまたぐ記録がない**。救急で書いた問題・実施・結果待ちを、入院時の記載で使えない。病棟の経過は、毎日、最初から書くことになる `[確認]`

- そのため、病棟の記載型（A05・A06・A07・A08）は、使える入力が少なく、多くの欄が「（未入力）」になる（段階3の報告のとおり）

### 8.3 全体像: 3つの層

```
スキーマ層            記録層                          場面層
（Modules から        （症例の記録。診察をまたいで     （場面ごとの入力・草案・記載・画面）
 構造だけ取り込む） ─→  積み上がる）                ─→
質問・段階・橋の分類   診察の連なり（救急→入院→経過…）  救急 / 外来初診 / 外来再診 / 入院時 /
場面の枠・目的         問題（安定ID）・観察・行為・       経過 / 中間サマリ / 退院時サマリ
記載型・入力の意味→欄  課題・決定・転換点               のプロファイル
```

- **スキーマ層**は、Modules が持つ構造（何を聞くか・何をどの欄に書くか）の取り込み。臨床の判断の中身は取り込まない（8.7）
- **記録層**は、RAG が持つ症例のデータ。いまの「症例の1枚」を、診察の連なりに広げる。記載は、記録からの**投影**（Modules と同じ考え方）。コピーした文章は原本ではない
- **場面層**は、スキーマ層と記録層の上に載る設定（プロファイル）。コードは1つで、場面ごとにデータが違う

### 8.6 積み上がる要素と、積み上げの規則

| 段 | その段で足されるもの（前の段のものは持ち越す） |
|---|---|
| 救急 | 背景（有効な時点つき）・時刻つきの観察・実施と予定（行為の状態）・問題（診断の確度は「疑い」から）・結果待ち・コンサルト・行き先の決定 |
| 入院時 | ベースライン・問題の優先順位・問題ごとの計画・治療目標と上限・退院の条件・コール基準 |
| 経過 | 日ごとの変化・問題ごとの推移（改善・不変・悪化・未評価）・計画の結果（実施・変更・中止と理由）・検査と時間・課題の完了 |
| 中間サマリ | 転換点（医師が印を付けたもの）・継続治療・デバイス |
| 退院時サマリ | 診断の確度の確定・退院時の状態・処方の変更と理由・フォローの課題（担当・期限） |

**積み上げの規則**（Modules の共通データの規則と、RAG のこれまでの約束から）:

1. **引き継ぎは医師の操作**。自動で書き写さない。持ってきた項目には「前の診察から」の印を付け、背景は有効な時点を添えて「再確認」を促す
2. **未入力は未入力のまま持ち越す**（陰性にしない）。陰性は、評価した陰性だけ
3. **計画は、予定のまま持ち越す**。「実施」は、医師が実施と記録したときだけ
4. 問題には**安定したID**を付け、診断の確度・管理の状態・推移を、別々に持つ
5. **訂正は新しい版**として残し、前の判断を上書きしない
6. **後日の事実を書かない**。要約は、その時点までに記録されたものだけから作る（Modules の「後日の酸素離脱は書かない」と同じ）
7. AI の草案から採用した項目の「AI草案」の印は、後の診察の記載にも引き継ぐ（コピーのとき外せる。今と同じ）
8. **日付は入れない**。時間軸は「病着からの分」「入院〇日目＋時刻」

### 8.7 Modules との境界

| 区分 | 内容 |
|---|---|
| **取り込む**（構造だけ。手で写さない。コミットを記録） | フローの質問（id・枠・ラベル・型・単位・選択肢・`core`・`required`）、段階、橋の分類（`neg`・`unable`・`wait`・`pend`・`unk`・`val`）、場面の枠の名前・順序・目的、記載型（済）、`ROUTES` |
| **取り込まない** | フローの**規則・鑑別・定義・軸**（臨床の判断の中身。「実使用で未検証・出典未照合」）。症候・問題・薬剤カードの本文（用量・閾値・事前確率）。訓練の採点 |
| **戻さない** | 実患者の情報、症例の記録、会話は、Modules に送らない。**Modules が RAG を呼ぶのは検索だけ**（変えない）。RAG で作った架空症例の下書きを Modules に入れるのは、医師が確認してコピーする形だけ（今と同じ） |
| **条件** | 取り込んだ Modules の内容を、臨床の主張として回答に混ぜない。Modules の臨床の中身を RAG の草案に使う話が出たら、`[Modules草案・未照合]` を付けて分け、**実装の前に医師に確認する** |

理由: RAG は実臨床の参考に使うので、出典未照合の訓練用の臨床の判断が、回答に混ざる害が大きい。構造（何を聞くか・何をどの欄に書くか）なら、その害がない `[推論]`。

### 8.8 データの扱い（方針に関わる）

- 症例の記録は、会話より長く残る必要がある（入院は数日〜数週）。いまの会話の保存（往復ごと、30日で消える）では合わない。**案**: 新しい表 `case_records`（1症例を1行のJSONで。上限つき）。保持は「最後の更新から N 日（仮に60日）」と、「この症例を終える（削除）」。**書き込み先が増える**ので、`CLAUDE.md` の書き込みの一覧を変える（医師の決定が要る）
- 時間は**相対だけ**（入院〇日目＋時刻、病着からの分）。絶対日付は、入れない・画面で促す（ガードは日付を検出しない。医師の決定どおり）
- 記録に入れてよいのは、これまでどおり年齢（歳の整数）・主要所見・検査値の数値まで。識別情報のガードは、記録のすべての自由記述の欄にかける
- **積み上がるほど、1症例の情報量が増え、特定されやすくなる** `[推論]`。相対時間・欄ごとの上限・自動削除・画面からの削除で抑える。稀な組み合わせへの注意（2.2）は、記録の画面にも出す
- 代わりの案: 記録を端末のメモリだけに置く（保存しない）。iPad の再起動で消える問題（段階1の発端）に戻るので、勧めない

### 8.10 リスクと限界

- **入力の重さ**: Modules でも、70〜88問を1つの画面で入れると重く、段階・中核・畳み・文からの振り分けで対処した（2026-10-17 の実測）。RAG は、中核だけを出し、自由記述の入口を残す。全問を並べない
- 構造を増やすほど、書く手間が増える。取り戻す手段は、引き継ぎ（D）と、文からの振り分け（G）。振り分けは提案で、確認した項目だけが記録に入る
- Modules の構造が変わると、取り込みが古くなる。取り込みのコミットの記録・`--check`・テストで検出する（記載型と同じ）
- **複数の受診の統合は、Modules でも未実装の課題**。最初に縦の一本（救急 → 入院時）で形を確かめてから広げる
- 草案（AI）には、前の診察の全文でなく、記録の要約（問題・実施・結果待ち）を渡す。費用と取り違えを抑える `[推論]`
- **病棟の場面（入院時・経過・退院）は、Modules にまだ scenes・flows がない**。型（欄）だけを使うので、入力の細かさは救急より粗くなる。Modules で先に作る（訓練・架空症例。Modules の roadmap にある未了項目）と、RAG はそれを取り込める。RAG で先に始めるなら、記載型の欄を入力の骨格にする
- 本物の API・実際の症例での確認が、いまもない。積み上げる前に、段階2〜4の実機の確認（書きぶり・採用の単位）を済ませたほうが、手戻りが少ない `[推論]`

### 8.12 自由記述からの取り込み（案 G の詳細。2026-10-24 の医師の問い: 「API を駆使すれば項目を選ばずに取り込めるか。足りない分は項目の選択で補えるか」）

**答え**: **できる。ただし、「項目を選ばずに入れる」ことと、「項目を選ばずに確定する」ことは別**。流れは、自由記述 → 抽出（提案）→ 医師の確認 → **足りない項目を選択で補う**。これは Modules が設計済みの方式（`docs/api-extraction.md`。入力の重さへの答えとして作られた）と同じで、RAG の側にはまだない。

```
自由記述を貼る／書く ─→ 場面を1タップで選ぶ ─→ 抽出（API。提案だけ）─→ 確認（元の文の該当箇所つき）
                                                                          │
         記録に入る（確認した項目だけ）←── 足りない項目を、選択肢のチップで補う ←─┘  （未入力は空欄のまま）
```

**いま（2026-10-24）すでにできること**: 症例の欄に自由に書けば、草案（AI）はそのまま読む（構造は要らない）。**構造が要るのは、機械的な抜けの検査（案E）・記載を型の欄に入れること・診察をまたぐ記録（案C）**。つまり、8の積み上げの土台のための取り込みで、草案のためではない。

**1. 抽出が得意なこと・危ないこと**（Modules の誤りの型 E1〜E7。`docs/voice-eval.md`。**Modules は型と評価の台本18本を作ったが、精度の実測の記録はまだない** `[確認]`）:

| 型 | 例 | 害 | 対処 |
|---|---|---|---|
| E1 | 「酸素を投与して」を「実施済み」にする | 必要な対応が抜ける | 行為は、文に実施と書かれたときだけ。予定は予定のまま（行為の状態を上げない） |
| E2 | 否定・不確かさの取り違え（「左右差はない」を「あり」） | 所見が逆になる | 否定・不確かさは、**元の文を並べて**確認する。陰性は、文に書かれているものだけ |
| E3 | **言及なし・未評価を「ない」「ある」にする** | 未入力が陰性になり、警告が消える | **最重要**。書かれていないものは、提案しない（空欄のまま）。「評価していない」と書かれたものは、評価不能 |
| E4 | 発言の主の取り違え（家族・救急隊の報告を医師の所見に） | 出どころが失われる | 情報源を項目に付ける（本人・家族・救急隊・紹介状） |
| E5 | 数値・単位・桁の誤り | 意味が逆になる | 数値は元の文の文字列と**一致を機械で検査**（単位つき）。一致しなければ捨てる |
| E6 | 数値から区分を推論する（血糖48 →「低値」） | 判断を医師から奪う | 区分は提案しない（記録するだけ） |
| E7 | 時刻の解釈（「十時」の午前・午後、「10分前」の基準） | 経過の時刻が狂う | 基準の時刻を画面で指定し、解釈した時刻を確認の画面に出す。相対時間で持つ |

**2. 確認の設計**（速さと見落としの両立）:

- 提案は、**確認するまで記録に入らない**。確認していない項目は、機械的な抜けの検査にも、草案にも、記載にも使わない
- 確認の画面は、各提案に**元の文の該当箇所**を添える（どこから取ったかが見える）
- **危険の度合いで確認の重さを変える** `[推論]`: 低い（年齢・性別・数値と単位が元の文の文字列と一致するもの）は、まとめて確認できる。高い（陰性・実施・評価・時刻・情報源の違うもの）は、**1件ずつ**。まとめて確認の既定は「選ばれていない」にする（見ずに全部通すことを避ける）

**3. 足りない分を、項目の選択で補う**:

- 抽出のあと、場面の**中核の質問のうち、まだ空欄のもの**を、機械で出す（AI ではない。案E。Modules の `core` と段階）。空欄は、段階ごとに、**選択肢のチップ**（Modules の質問の選択肢）で、1タップで埋める
- **「なし」にするのは、医師が選んだときだけ**。未入力を、まとめて「異常なし」にするボタンは作らない。代わりに、「言及のなかった陰性所見」を、段階ごとの**複数選択のリスト**で出し、**医師が評価したものだけ**に印を付ける（印を付けたものが、評価した陰性になる）
- 数値・文の項目（バイタル・検査値・時刻）は、チップでなく、入力欄で補う

**4. 作り方**（いまの設計から）:

- **場面は、医師が1タップで選ぶ**（スキーマが場面ごとなので。文から当てさせない。違ったとき、取りこぼしが出る）
- スキーマ層（案A）の質問の一覧から、**構造化出力のスキーマ**を作る。質問ID・選択肢IDの**列挙の外の値は、返らず、返っても捨てる**。数値は、質問の単位と検証を通らなければ捨てる
- 質問の一覧と抽出の規則（毎回同じ部分）を先頭に置き、**プロンプトのキャッシュ**にする。モデルは、Modules と同じ Sonnet 5.5 の low から測る `[推論]`。**待ち時間と費用は、まだ測っていない** `[未確認]`（1回の貼り付けで1回の呼び出し。入力のほとんどはキャッシュ。数秒〜十数秒、数円以内の見込みだが、実測が要る）
- 何度かに分けて貼れる（追記）。前の確認済みの項目と食い違うときは、**上書きせず**、新しい版として並べて見せる（訂正の規則）
- 抽出は、**事実だけ**。鑑別・危険・診断を言わせない（Modules と同じ）。草案（AI）とは別の呼び出し

**5. データの扱い（方針に関わる）**:

- **貼った原文は保存しない**。送って、提案を作って、捨てる（Worker は保存・ログなし）。保存されるのは、**確認した項目だけ**（`case_records` などの、決まった欄）
- **貼り付けは、氏名・日付・ID が入りやすい**（電子カルテからのコピーなど）。現在のガードは、ID・電話・メール・識別の語を検出し、**氏名と日付は検出しない**（医師の決定 1b）。長い文では、見逃しの害が大きくなる `[推論]`。**案**: 貼り付けの入口に限って、(a) 文字数の上限（例 4,000字）、(b) **日付らしい文字を、送る前に見せて、経過日数に直すよう促す**（止めない。確認すれば送れる）。これは 1b の「ガードは日付を検出しない」の例外ではなく、入口に添える注意だが、**決めてもらう**
- 抽出の結果の確認前の提案は、画面のメモリだけ（保存しない）

**6. 測り方**（実装の前に）:

- Modules の**訓練症例48例**（架空。質問IDつきの正解 `[case.answers]` と想定する critical つき）から、**模擬の記載文**（救急の記載のような、箇条と略語の入ったメモ）を作り、抽出の結果を正解と突き合わせる。**的中・欠落・余計・誤り**を、E1〜E7 の型別に数える（Modules の評価の様式）
- **E1・E3（指示を実施にする・未評価を陰性にする）は、1件でも出たら、規則を直す。目標は0件**（Modules と同じ基準）。それ以外は、種類別に報告して、医師が許容を決める
- **この環境には Anthropic の API キーがなく、本物のモデルでは測れない**。医師の実機か、キーを入れた環境で回す

**7. 限界**:

- 精度は保証できない。確認の手間はゼロにならない（提案を見る時間）。速さの利益は、**確認が軽いこと**と**足りない分のチップ**で出す
- 端末の音声入力で文を作るときは、同音語・専門用語の誤認識（E8）が加わる。文字になった時点で、同じ確認を通す
- 場面のスキーマ（案A）が前提。**先にスキーマの取り込みと中核の未入力の検査（段1）**を作り、そのあとで抽出（G）を足す
- 文の長さ・書き方の癖（略語・箇条・時系列の混在）で精度が変わる。実機の例（匿名化した書き方の例ではなく、書き方の型だけ）で、評価の台本を足していく

8.11 に足した決定 6・7 も、同じ日に決まった（上限なし・日付の確認なしで自動変換・原文は保存しない）。

### 8.13 段2の実装（救急 → 入院時の症例の記録。2026-10-24。医師の決定 1e の2・3・5・6 を受けて）

**範囲**: 救急の症例（段1までの入力）に、引き継ぎ・問題の板・入院時の記載の下書き（A05）を足し、**サーバーに保存して開き直せる**ようにする。経過（A06）・中間サマリー・退院時サマリーは段3。

**保存層（Worker）** `worker/src/recordstore.ts`・`/api/records`: 表 `case_records(id, title, created_at, updated_at, rev, payload)`。文書は1症例1行の JSON（`v: 1`・`title`・…）。Worker は文書の中身を解釈せず、**限界・識別情報・版**だけを見る（Worker は臨床の判断を持たない）。
- 限界: 30件・1件 400,000 字（段3で 200,000 から引き上げ。8.14）・1つの文字列 8,000 字・深さ 8・キーは `[A-Za-z0-9_.-]{1,64}`（文字をキーに隠せない）
- **識別情報**: 文書のすべての文字列（入れ子の奥まで）を `scanAll` にかけ、見つかれば何も書かずに 400（種類の名前だけを返す）。日付は検出しない（決定 1b）が、日付は文書に入る前に画面が直す
- **版**: 作成は版なし（0）、更新は直前に読んだ版。違えば 409（現在の版を添える）。消えた記録への更新は 404（作り直さない）
- **保持**: 最後の「更新」から N 日（`CASE_RECORD_RETENTION_DAYS`。既定 60）で、一覧・読み・保存のたびに消す。読むだけでは延びない。「終える」＝削除
- 書き込みの一覧に `case_records` を足し、`worker/test/conversations.test.ts`（書き込みの表と元のファイル）と `worker/test/records.test.ts` で固定

**記録のモデル** `web/case-record.js`（純関数。画面・通信・保存・AI に触れない。テストが検査する）:

```
記録 { v, title, ed: { case, adopted: [{ id: a1…, role, heading, text, cites, to, entry? }] },
       adm: { route, summary, baseline, general, outlook },        // 先生が書く入院時の欄
       problems: [{ id: p1…, label, certainty, from: typed|ed, assess: [{id: i1…, text, from, cites?}], plan: [{…, state, reason?}] }],
       contingency: [エントリ],  seq: { p, i, a } }
```

- **安定 ID**: `seq` が次の番号を持つ。問題・項目・採用の番号は、消しても、読み直しても、再利用しない
- **引き継ぎ**（`attach`）: 採用した項目を、先生が選んだ先（新しい問題／ある問題／コール基準／持ってこない）に置く。AI 由来（`from: "ai"`）と出典を保ち、**計画は「予定・検討」で着く**。選び直すと、前に作ったエントリを取り下げる。**採用しただけでは板に何も入らない**
- **積み上げの規則（8.6）の対応**: 1 引き継ぎは医師の操作／2 未入力は未入力のまま（確度も空欄）／3 計画は予定のまま（実施・中止は先生が選んだときだけ）／4 問題に安定 ID／8 日付は入れない。**5（訂正は新しい版）・6（後日の事実を書かない）・7（AI の印の持ち越し。AI 由来の行は印を保つ）のうち、5・6 は経過（段3）で効く**
- **時間軸**（`timeline`）: 回答した時刻の質問を、フロー自身の起点の質問（病着）からの分で並べる。起点より前の時刻は翌日と見なして印を付ける。時刻に結ばれた所見（橋の `at`）を、選んだとおりに添える。**判定しない**
- **注意**（`checks`）: 入力の状態を数える。判定の語（正常・異常・遅れなど）を使わない（テストが検査する）
- **日付**（`relativizeRecord`）: 貼り付け・欄を離れたとき（`bindDates`）に加えて、**保存の直前**に、記録のすべての自由記述を「N日前」「入院N日目」へ直す
- **入院時の記載（A05）**: `assemble("A05", { kase, items: [], board })`。`FILL` の `b:` の出どころ（先生の5欄・問題リスト・問題別の A/P・コール基準）を足した。他の記載の型は `board` を無視する（テストが検査する）。持ってきていない採用項目は入らない

**画面** `web/record-ui.js`: ヘッダーの「症例の記録」と、固定中の症例の横の「記録」（連動中は「記録（連動中）」）。一覧（開く・終える）→ 記録（救急: 時間軸・注意／入院時: 引き継ぎ・問題の板・先生の入力・記載の下書き）。変更は少しあとに自動で保存し、状態を常に出す。固定中の症例を直して固定し直すと、記録の救急の症例が更新される（別の症例を会話などから固定した場合は、連動が外れる）。ブラウザの保存領域には置かない（テストが検査する）。

**独立レビューを受けた修正（PR #11 のマージ後。2026-10-24）**: 別の目で「識別情報・日付・AI の印・計画の状態・版の競合・別の患者の混入」を破れないかを調べさせ、再現できたものを直した。
- **版の確認が原子的でなかった**（同じ版からの2つの保存が両方通った）→ 書き込みの条件に `WHERE rev = ?` を足し、変更行数が0なら 409。作成の主キー衝突も 409。書き込みが変更行数を報告しない場合は、通ったものと見なさず失敗にする
- **キー・数値は検査していなかった**（値の文字列だけ）→ キーも検査にかけ、英字始まり・5桁以上の数字の連続なし。9桁以上の数値は断る
- **別の患者の混入**: ①記録を開いても画面の会話（履歴・保存先の会話）が残った → 開くときに、固定中の症例がこの記録の版のどれでもなければ新しい会話にする（確認つき）。②別の症例の回答の採用が開いている記録に入りうる → 記録が持った症例の版（短いハッシュだけを保存）に無い回答なら確認。③別の患者の症例を固定し直すと記録の救急の症例が上書きされた → 年齢・性別が違えば確認し、キャンセルで連動を外す。症例の画面にも連動中を出す
- **画面の保存**: 保存中に直した分が、一覧へ戻る・症例を外すと黙って消えた → 保存の完了を待ち、保存できていなければ確認する。「競合」「見つからない」の状態を編集が上書きして偽の「自動保存」と出した → 状態を保つ。**答えが届かなかった保存が、自分の保存との自己衝突になった** → 409 のとき、サーバーの内容が直前に自分が送ったものと同じなら、版を取り込んで続ける。別の記録の応答を、記録の ID でなく開いた回で見分ける。保存中に日付を直しても画面を描き直さない（入力の途中の焦点・変換を壊さない）。二重タップで2件作らない
- **日付**: 最初の保存（`createFrom`）・採用項目の文・記載の下書きの表示にも相対化をかける（元の日付は、保存前も表示も残らない）。**残る限界**: 「3日前」のような相対表現は入力した日が基準で、日がたつとずれる（記載に基準は付かない）。サーバーが持つ作成・更新の時刻は、保持期間のための絶対時刻（本文ではない）
- **時間軸**: 病着より前の出来事（発症・最初の発作・最初の出血）を翌日と見なして「+1300分」と出した → 日付のない時刻は**読み方を仮に決めて印を付け、先生が「病着の前／後（翌日）」を切り替えられる**ようにした（切り替えは記録に保存）。「いつ始まったかを尋ねる時刻の質問」は、構造ではなく入力の意味なので、`web/case-record.js` の `PRE_ARRIVAL`（3つ）に置く
- **引き継ぎの取り消し**: 「新しい問題」を外しても問題が残った・選び直しで先生の編集が消えた → 対称にした（上の clinical-use の 1e）。AI 由来の「新しい問題」に印と出典が付かなかった → 付ける。名前のない問題が内容ごと記載から消えた → 「（名前なし）」で入れる。ラベルの `[推論]` が出どころの印を外しても残った → 外す。`ROLES` の `constructor` などは `hasOwn` で除いた
- **取り込み（importer）**: 橋の `ent`・`status`・`phase` は決まった語だけ、`at`・`of` は質問の ID、`origin_q` は時刻の質問、`origin_label` は短く、どちらか片方だけは不可（文章が構造として入らないように）
- **直さなかった**: 保存の前に期限切れの記録を消してから 404 にする点（保持期間を過ぎて60日以上、保存せずに画面を開いたままだったときだけ。期限の意味どおり）

**限界・残り**
- 記録は1症例の「救急 → 入院時」だけ。**受診の連なりの続き（経過・転棟・退院）は段3**。入院時の欄の一部（ベースライン・全身管理）は先生が書くだけで、救急からの自動の持ち越しはない
- 採用の取り込みは、アセスメントとプランの草案の回答にある「症例の記録へ」だけ。草案の項目の「どの問題の評価か」は文から決められないので、先生が選ぶ
- 保存は、最後に書いた画面が勝つ形ではなく、**版が合わなければ断る**形（書き込みの条件でも確認する）。断られた画面の変更は保存されないので、記録を開き直す（画面に出す）。複数の端末で同時に編集する使い方は想定していない
- 60日（仮）を過ぎた記録は消える。入院が長引くときは、更新するか、保持を延ばす（`CASE_RECORD_RETENTION_DAYS`）
- **本物の API・実際の使い方での確認は、まだない**。使ってみて、問題の板の置き方（評価・計画の粒度）、引き継ぎの手数、注意の出し方を見る

### 8.14 段3の実装（経過・中間サマリー・退院時サマリー。2026-10-25。8.13 の続き）

```
         discharge: { decided, day, dest, procedures, state, followup,                           // A08
                      meds: [{ id: m1…, text, change: new|changed|stopped|continued|"", reason? }] } }
problems[]: + added, cert_log: [{ day, certainty }], dx: main|sub      plan[]: + added, log: [{ day, state, reason? }]
```

**積み上げの規則（8.6）の対応**
- **6 後日の事実を書かない = `asOf(rec, N)`**。問題・評価・計画・コール基準・課題に、加えた日（`added`。いまの日 `course.today` が刻印）。**履歴を持つ判断**（問題の確度・計画の状態と理由・課題の完了）は日つきで残し、N 日の記載は「N 日までに先生が記録した判断」だけを出す（N 日より後に確定した確度、実施にした計画、閉じた課題、後で決めた退院は入らない。課題の問題への紐づけも、その問題が N 日に無ければ外れる）。**課題の完了・再開も日つきの履歴**で、閉じたあとに再開しても、閉じた日の記載には「閉じていた」と出る。**刻む日は、いまの日と、そのものを加えた日と、すでにある履歴の最後の日の、いちばん後**（前の日に戻って判断を直したときは、すでに記録した最後の日からの記録になる。こうして、盤面の「いまの値」と、いちばん新しい日の記載が、いつも一致する）。履歴ができる前（段2）の記録は、最初に直したときに、それまでの値を「加えた日からの値」として履歴の最初に置く入院時の記載（A05）は `asOf(…, 1)`。「次の日へ」「前の日」でいまの日を動かし、記載の日は選べる
- **2 空欄は空欄**: 推移は先生が選んだものだけ（選ばなければ記載に推移の行は出ず、注意では「未評価」と数える。「不変」「安定」とは書かない。N 日に選んでいなければ、それ以前で最新の推移を、**その日つき**で出す）。確度・主病名/副病名・処方の区分も、選ばなければ空欄で、記載には「確度: 未選択」「区分未記入」「区分を選んでいない問題」と出る。**課題の種類（結果待ち・コンサルトの返事・フォロー・その他）も先生が選んだときだけ**（選ばなければ種類なしで、「結果待ち」と書かない。救急で「結果待ち」を選んだ項目だけが、「結果待ち」の課題になる）。文のない課題・処方の行は、記載にも注意にも出さない（開き直すと消える行なので）必須欄が空なら「（未入力）」、条件つきで空なら欄ごと出さない。担当・期限・変更の理由は「未入力」と出る（作文で埋めない）
- **3 計画は予定のまま**: 計画の状態は `planned / done / changed / stopped` で、`done`・`changed`・`stopped` は先生が選んだときだけ。前の日までの「予定のまま」は、画面に一覧し（その場で結果を選べる）、注意で数える（判定しない）
- **5 訂正は新しい版**: 確度と計画の状態は履歴（`cert_log`・`log`）で、後の変更が前の日の記載を書き換えない。自由記述（日ごとの文・課題・中間サマリー・退院時の文）は上書きで、履歴を持たない（下の限界）
- **7 AI の印**: AI 由来の問題・評価・計画は、A06・A07・A08でも「〔AI草案〕」と出典・「〔救急から〕」を保つ（問題の見出し・主病名/副病名・推移の行・課題の問題・「区分を選んでいない問題」。コピーで別々に外せ、印を外すと名前の中の `[推論]` も外れる）。AI の計画が「実施」になることはない
- **8 日付は入れない**: 日ごとの文・推移のメモ・課題の文/担当/期限・中間サマリーの4文・退院の4文・処方の文/理由・計画の理由の履歴も、貼り付け・欄を離れたとき・**保存の直前**・記載の表示で「N日前」「入院N日目」に直す（`relativizeRecord`）

**3つの記載**
- **A06（病棟の経過）** `progressNote(rec, 日)`: その日の6つの文（先生の入力）と、問題別の A/P（その日の確度・計画の状態と、その日までで最新の推移）
- **A07（転棟・中間サマリ）** `interimNote(rec, 日)`: 型の取り込みはあるが、症例だけの記載の画面には出さない（`RECORD_ONLY`。`fill` を渡さないと組み立てが断る）。「これまでの経過と転換点」は、先生が**転換点としてマークした日**（★）のその日の記録と推移で、マークがなければ「（未入力）」。管理中の問題と方針は、その日の A/P。結果待ち・未解決は、その日に開いている課題（担当・期限つき）。転棟先・現時点の状態・継続治療・引継ぎは先生の入力。「入院N日目の時点の記録です。確度・計画の状態・推移・課題の完了は、その日までに記録したものだけです。文章（問題名・評価・計画・先生が入力した文）は、最後に編集したものです」の行を付ける（文章まで「その日のもの」と言わない）
- **A08（退院時サマリ）** `dischargeNote(rec)`: **先生が「退院を決める」を押し、退院の日が入っているときだけ**組み立てる（そうでなければ null。記録が終わっただけでは退院にならない）。退院の日の時点の記録から。主病名・副病名は先生が各問題で選んだもの（確度はその日のもの。選ばなかった問題は「区分を選んでいない問題」に並ぶ）、Problem 別の経過（推移を日ごとに並べる・評価・計画の結果。何も無い名前だけの問題は「（未入力）」）、転換点（その日の「前回からのイベント・主観的症状・所見や検査の推移・患者全体の状態」。栄養・活動・翌日の確認は入らない）、退院時処方（新規・変更・中止・継続と理由。変更・中止で理由がなければ「理由: 未入力」）、結果待ち・担当・期限（その日に開いていた課題）

**画面** `web/record-ui.js`: 「経過（日ごと・課題）」（いまの日・前の日までの計画の結果・日の文・転換点のマーク・問題ごとの推移・課題・A06 の下書き）、「中間サマリー・転棟（A07）」、「退院時サマリー（A08）」（退院を決める・退院の日・4つの文・処方・下書き）。問題カードに「退院時サマリーでの扱い（主病名／副病名）」。開閉した節は、画面を描き直しても保つ。ブラウザの保存領域には置かず、通信は `/api/records` だけ。

### 8.15 段4a: 文章からの取り込み（案 G。2026-10-25。8.12 の実装）

**範囲**: 「場面・症候の質問で入力する」の中に「文章から取り込む（試作）」を足す。メモ（申し送り・紹介状の抜粋・ご自身のメモ）を貼ると、開いているフローの質問への答えの**提案**を作り、**先生が確認したものだけ**が答えに入る。場面別の草案と、問題ごとの書籍の根拠の持ち越し（案 F）は段4b。

**守る線**（8.12 と、決定 1e の6・7 のとおり）
1. **提案は答えではない**: 先生が「入れる」を押すまで、答え・記載・中核の未入力の数・次に聞くこと・記録のどれにも効かない
2. **貼った原文は保存しない**: Worker は保存せず、ログにも書かない。画面もそのタブのメモリだけ（`sessionStorage`・会話の保存・症例の記録に入れない）。場面を変える・症例を外す・「新しい会話」・「文章と提案を消す」で消える
3. **識別情報らしき文字があれば送らない**（画面。Worker も 400 で断る。**「それでも送る」はない**: 質問の入力と違い、長い文は直してから送る）。氏名と日付は検出しない（決定 1b）が、**日付は送る前に「N日前」「入院N日目」へ自動で直す**（貼り付け・欄を離れたとき・送る直前）。画面は、氏名・ID・生年月日・電話番号を消してから貼るよう言う
4. **書かれていないことは提案しない**（E3）。「なし」にするのは、メモにそう書かれているときだけ。医師の判断・方針・処置の予定は、事実として提案しない

**モデルに聞くのは事実だけ**（`web/extract-model.js` の `extractable`。生成する質問の一覧もこの1つの関数から作る）: 質問の「入力の意味」（Modules の橋の分類）が、病歴・所見・時刻・行った処置・測定の条件のものだけ。**判断（数値の区分・臨床確率・重症度）、方針（コンサルト・行き先・申し送り・治療目標）、理由、症例自身の欄（年齢・性別）、ラベルまたは選択肢に「判断」「医師の」とある質問、そして `JUDGMENT_IDS`（入力の意味は所見でも、実は医師の読み・決めである質問: 第一印象・救急隊の報告の「安定／不安定」・「比べた経過（改善・不変・悪化）」・循環の評価・現場の血糖の区分・外液や鎮痛への反応・失神かの判断・歩行時 SpO2 や HINTS の読み・耳石置換法の結果・血液培養や解熱薬の決め、など。独立レビューで洗い出した）は、そもそもモデルに見せない**（数値から区分を決める誤り E6 を、仕組みで防ぐ。`JUDGMENT_IDS` の ID が取り込んだスキーマに無くなったらテストが落ち、見直しになる）。救急の呼吸困難なら 69 問中 36 問

**確認の重さ**（`classify`・`whyHigh`）: 各提案を、**まとめて確認できる**ものと**1件ずつ確認する**ものに分ける。1件ずつ: 選んだ選択肢が「異常なし・陰性」「不明」「評価不能」「未実施」「結果待ち」「全体を否定する（特になし）」のもの（**そのうえ、引用にも前後にもそう読める言葉がなければ、「書かれていないことを『なし』にしていないか」を添える**）／選択肢の自分のラベルが「なし・正常・未・不明」と読めるもの／時刻／行った処置（質問のラベルや ID が処置・投与・施行を言うものを含む）／測定の条件／**元の文（引用と、その一文）に否定・不確かさ・予定や指示・概数や範囲の言い方があるもの**（否定は「ない」「聴取せず」「認められず」「否」「no」「w/o」など、疑いは「と思う」「らしい」「未評価」など、概数は「約」「程度」「以上」など、広く取る。足りない語は見つけ次第足す）／**引用が、その質問・選んだ選択肢の言葉と2文字の重なりもないもの**（無関係な数値や、数値から区分を読んだもの。「乳酸 4.2」が「乳酸の上昇」にならない）。まとめて: それ以外の事実（数値・所見）。**どれも最初は選ばれていない**（「すべて選ぶ」は先生が押すボタン）。入力済みの答えと違う提案は、「入力済み／提案」を並べ、**既定はそのまま**（「上書きして入れる」を押さない限り変わらない）。いまの答えでは表示されない質問への提案は、先にその条件を満たす答えを入れるまで入れられない。各提案に、**元の文の該当箇所（引用）と、その一文**を添える

**作り方**
- Worker `POST /api/extract`（`worker/src/extract.ts`。保存なし・ログなし）。`{ flow, schema, text }` を受け、質問の一覧（`worker/src/extract-catalog.ts`。`scripts/build_extract_catalog.mjs` が `web/flow-schema.js` から生成。`--check` と `worker/test/extract.test.ts` が古さを検出。**規則・鑑別・ヘルプ文は入れない**）の版（`schema`）が画面と違えば 409。モデルは設定の `MODEL`（既定 Sonnet 5.5）、1回の呼び出し（ストリームなし）、**構造化出力**（質問 ID の列挙・値は文字列の配列・根拠の断片）、思考の深さ `low`、プロンプトキャッシュ（指示と質問の一覧が先頭。フローごとに同じ文字列）、サンプリング指定・強制ツール呼び出しなし（Claude 5.5 は受け付けない）、拒否時の代替（`fallbacks: "default"`。API が受け付けなければ付けずに1回やり直す）
- **応答の検査は二重**（Worker と画面。`tests/vectors/extract.json` を両方に通す）: 質問がフローにあるか／引用が文にあるか（NFKC・空白・大文字小文字を無視。**句読点・記号を除いて2文字以上**）／値が質問の受け付けるものか（選択肢の id・排他は単独・**数値は引用に書かれた数字**・**時刻は引用に書かれた時刻（時も分も。「10分前」「2時間前」は時刻でなく、午前・午後の印のない3時は03:00）**・文の質問は**メモの言葉そのままで、引用と重なり**、メモにない数字を含まない）／同じ質問が2回あれば**どちらも捨てる**。捨てた数は理由別に数える（本文は入れない）
- 1回の文章の上限は **20,000 字**（技術上の上限。決定 6「上限なし」の実装上の値で、分けて貼れる）。1日の利用上限は `/api/ask` と同じ数に数える（識別情報で断ったものは数えない）。**書き込みは増えない**
- 画面: `web/extract-ui.js`（`initIntake` の中。`api` を渡す）。通信は `/api/extract` だけ。年齢・性別は症例自身の欄があるので取り込まない。識別情報の検査は、メモそのものと、**全角を半角にし、見えない文字を除いた形**の両方にかける（Worker も同じ）。モデルは `MODEL`（`/api/ask` と同じ）か、設定した `EXTRACT_MODEL`。応答の `model` は、代替で答えたモデルがあればそちら

**測り方**（`docs/evaluation.md`）: `eval/run_extract_eval.ts`。先生が書いた架空のメモ（氏名・ID・日付なし）と、そのメモが支える答え（`expect`）、**支えない質問（`must_not`）**から、的中・欠落・誤り・余計と、**forbidden（支えない質問への提案）**を数える。**forbidden は1件でも出たら規則を直す。目標は 0**（Modules と同じ基準）。この環境には API キーがなく、**本物のモデルでは測れていない**

**テスト**: `worker/test/extract.test.ts`（一覧の生成・要求・プロンプト・スキーマ・応答の検査・呼び出し・HTTP・保存しない・評価の部品）、`worker/test/extract-model.test.ts`（画面側の検査・重さ・衝突）、`tests/e2e/ui_extract.py`（偽のモデルで画面を通す）

**独立レビューを受けた修正（PR #15 のレビューで。2026-10-25）**: 別の目で「判断が提案されないか・誤った値が検査を通らないか・まとめて確認に紛れないか」を破れないかを調べさせ、再現できたものを直した。
- **判断にあたる質問が「事実の質問」として一覧に残っていた**（ラベルが無害でも、第一印象・救急隊の報告の安定／不安定・「比べた経過」・循環の評価・現場の血糖の区分・血液ガスの「（医師の判断）」の選択肢など）→ `JUDGMENT_IDS` と、選択肢のラベルの検査を足した。生成した一覧に「判断」「医師の」の選択肢が無いこと、`JUDGMENT_IDS` が実在することをテストが検査する
- **引用が質問と無関係でも、まとめて確認に入った**（「BP 120/80」から胸痛の性状、1文字の引用、数字だけが合う呼吸数）→ 引用は2文字以上に。引用が質問・選択肢の言葉と重ならなければ1件ずつに回す。「なし・陰性」を選ぶのに、引用にも前後にも「なし」と読める言葉がなければ、その旨を添える
- **否定・不確かさの言い方の網が狭かった**（「なかった」「聴取せず」「認められず」「否」「no」「w/o」「と思う」「約」「以上」など）→ 広げた（34通りを表にしてテスト）。文の質問は、値の側の一文も見る
- **時刻は時だけ検査していて、分も「10分前」も通った**（「10:45」を「10:20」から、「10:30」を「10分前」から、午前・午後の取り違え）→ 引用に書かれた時刻（時と分）そのものだけ通す。午前・午後の印がなければ時は書かれたとおり。共通のテストベクトルに足した
- **「選んだ」の印が古くなった**（選んだあとに手で答えると、「選んだ 1 件」と出たまま／答えを消すと選ばれた状態で戻った）→ 描き直すたびに、まだ「まとめて」にあるものだけに絞る。「入れる」を押した時点で、もう一度、新しく・まとめてよいものだけを取る。開いた「同じ答え」「いまは入れられない」の一覧は、描き直しても開いたまま。中断を「提案なし」と取り違えない
- 識別情報の検査を、全角・半角・見えない文字を直した形にもかけた（「ID」＋見えない文字、半角カナの「ｶﾙﾃ番号」）。応答の `model` は答えたモデル。`EXTRACT_MODEL` を足した。評価（`eval/run_extract_eval.ts`）は、**支えない質問への提案が「まとめて確認」に入ったか**も数える
- **直さなかった**: `ID A1234567`（英字つきの番号）や `1234 5678`（空白で区切った数字）は、既存の識別情報の網（決定 1b。質問の入力と共通で、画面と Worker の双子）が見つけない。この入口だけの特別扱いはしていない（網を広げるときは、双子と共通のテストベクトルを一緒に直す）／各提案を入れたあと、次のカードが同じ位置に来る（二度押しの余地。実機で見る）

**限界・残り**
- **本物の API での確認はまだない**（待ち時間・費用・取りこぼし・誤りを、実機の初回で `eval/run_extract_eval.ts` で測る）。構造化出力のスキーマ・`fallbacks` の受け付けも、実測で初めて分かる。デプロイの前に、`--local`（Worker を通さず Anthropic API に直接。同じ指示・スキーマ・検査のコード）と、架空のメモ15件 `eval/extract.invented.jsonl` で先に測れる（`docs/evaluation.md` 3.3b）。Worker の経路（合言葉・上限・環境変数）と実機の操作は、デプロイ後に確かめる
- 引用の検査は、モデルが**文にある言葉を引用したか**までで、**引用と値の意味が合うか**は機械では分からない（引用が「胸痛」で値が別の性状、など）。そのため、否定・不確かさ・予定の語を、引用だけでなくその一文まで見て、1件ずつ確認に回す。**日本語の否定・不確かさの言い方の網は一部**（足りない語は見つけ次第足す）
- 時刻は、メモに時刻が書かれているものだけ（「30分前」「昨夜」は提案しない。相対時間の解釈は未対応）。年齢・性別は取り込まない
- 文の質問（血圧・脈拍など）は、メモの言葉そのままの写し。誤字・略語もそのまま
- 追記（何度かに分けて貼る）は、新しい文章で提案を作り直す（前の提案は消える）。確認済みの答えは残る
- 段4b（場面別の草案・根拠の持ち越し）は、実装済み（8.16）

### 8.16 段4b: 場面別の草案と、問題ごとの書籍の根拠の持ち越し（案 F。2026-10-25）

**範囲**: アセスメントとプランの草案に**場面**を選べるようにし（見出しが場面ごとに変わる）、病棟の場面では**開いている症例の記録の要約**を草案に渡し、**問題ごとに見た書籍の頁**を記録に持ち越す。新しい表・書き込みはない（`case_records` の文書の中身が増えるだけ）。Modules 側は変えていない。**作成者の案で、書きぶりは本物の API で医師が数例見て決める**（8.9）。

**守る線**
1. **場面は見出しと、その下に書く内容を変えるだけ**: 事実を足さない。重症度の等級・推移・確度・実施・担当・期限は、草案が決めない（先生が選ぶ）。数値（用量・閾値）はこの層に書かない（テストが検査する）
2. **記録の要約は、先生が記録したものを、その日までの分だけ**: `asOf` で切った記録から作る。**履歴を持つ判断**（確度・計画の状態と理由・推移・課題の完了）は、その日までのもの。**履歴を持たないもの**（問題名・評価と計画の文・問題の順序）は、いまのもので、要約の先頭の1行と `renderBrief` がそう言う（「後日の事実は含みません」とは言わない）。日付・前の診察の全文・書籍の頁は入れない。未記入は未記入のまま（「確度: 未選択」「担当: 未入力」）で、文のない行は行にしない。AI の草案を採用した行は「（AI草案を採用したもの）」と印を付け、モデルに「新しい事実の根拠にしない・実施済みと書かない」と伝える（`BRIEF_RULES`）。**その行の数値は先生の入力ではない**ので、回答の数値の突き合わせから除かない（`userBrief`）
3. **渡す内容は送る前に画面に出す**: 場面を選ぶと、要約を「草案に渡す記録の要約（送る内容）」として見られる。送ったあとも、そのターンに「送った症例の記録の要約」として残る（この画面のメモリだけ）。**会話には保存しない**（保存するのは場面の名前だけ）
4. **書籍の根拠は「どこを見たか」で、書籍が支える確認ではない**: 残すのは題名・頁・節の名前だけで、本文は残さない。AI に書籍を引かせない（検索は問題の名前で、LLM を呼ばない既存の `/api/search`）

**場面**（`web/draft-scenes.js` と `worker/src/prompt.ts` の `SCENE_SECTIONS` が双子。`worker/test/scenes.test.ts` が見出しの文字・順序・役割を固定）

| 場面 | 見出し（役割） | 記録の要約 |
|---|---|---|
| 救急外来 | 問題リスト（問題）／重症度と安定化（計画）／critical の除外の根拠（評価）／検査は何を区別するか（計画）／行き先・帰宅条件・申し送り（コール基準） | 渡さない |
| 外来初診 | 問題リスト／鑑別と除外の根拠（評価）／検査の目的（計画）／再受診の基準（コール基準） | 渡さない |
| 病棟・入院時 | 問題リスト（優先順位つき）／各問題の評価／各問題の計画／治療目標・退院条件／コール基準 | 記録を開いていれば渡す（**入院1日目の時点**。入院時の記載と同じ。なくても作れる） |
| 病棟・経過 | 前回からの変化（読むだけ）／問題ごとの更新（評価）／計画の変更案と、その理由（計画）／新しく立つ問題（問題）／翌日の確認・コール条件 | **要る**（なければ選べない。Worker も 400） |
| 中間サマリー・転棟 | 経過の要約（読むだけ）／問題ごとの現在の評価／継続する計画と結果待ち／悪化時の再評価・連絡条件 | **要る**（転換点の日・中間サマリーの先生の入力・問題ごとの推移の記録も入る） |
| 退院時サマリー | 経過の要約（読むだけ）／診断ごとの根拠（評価）／残る課題（計画。担当・期限は書かない） | **要る**（退院を決めていれば退院の日の時点。転換点の日・問題ごとの推移の記録・主病名/副病名も入る） |

どの場面も、最後の2節（確認すべき数値・書籍に見つからなかった点）は草案自身の節で、採用できない。「前回からの変化」などの要約の節は読むだけで、採用の印は付かない。採用の役割（問題・評価・計画・コール基準）は、これまでの「症例の記録へ」の引き継ぎ（`attach`）にそのまま使われる（場面の見出しも `headingRole` が読む。共通の見出しの役割は変わらない）。**外来再診（A02）の場面（AI の草案）は作っていない**（外来の記録は 8.19 で持ったが、場面の指示は `prompt.ts` に足す変更で、医師の確認の後）。

**API**: `POST /api/ask` に `scene`（上の6つ。`mode: "assess"` のときだけ）と `record_brief`（要約の文字列。上限 `BRIEF_LIMIT`＝5000字。`casemode.ts` と `web/draft-scenes.js` が双子）。400: `bad_scene`／`scene_needs_assess`（assess 以外）／`record_required`（経過・中間・退院で要約なし）／`brief_needs_scene`（要約を受けない場面・症例なし）／`bad_brief`。**要約は症例と同じ識別情報の検査にかかる**（`possible_identifier`。確認すれば送れる）。要約は症例の直後・【依頼】の前の最後のユーザーメッセージにだけ付き、履歴には入れない。第2のシステムブロック（`caseSystem(mode, hasOwn, scene, hasBrief)`）の見出しが場面のものになり、要約があれば記録の規則が付く。基本のシステムプロンプト（キャッシュされる先頭のブロック）は変わらない。

**記録の要約**（`web/record-brief.js`。画面・通信・保存・AI に触れない純関数）: `recordBrief(rec, day, { scene })` は、その日の時点の記録から、問題（優先順位順。確度・推移・評価・計画の状態と理由）、その日の先生の記録（前回からのイベント・主観的症状・所見や検査の推移・患者全体の状態）、未完了の課題（担当・期限は「未入力」と出す）、コール基準を並べる。**場面ごとに入るものが違う**: 主病名/副病名は退院時サマリーだけ（退院時サマリーのための先生の選びなので）／中間サマリー・退院時サマリーには、転換点の日（その日の先生の文）と、問題ごとの推移の記録（その日までに選んだものすべて）が入り、中間サマリーには、あわせて中間サマリーの先生の入力4つが入る（場面の指示が指している情報を、要約が持つ）／経過は、最新の推移だけ。長いときは、文を短くし、それでも長ければ優先順位の低い問題から外し、それでも長ければ末尾の行を、**行の途中で切らずに**外して、その旨の1行を入れる（`truncated`・`omitted`・`omittedLines`）。日は、入院時の場面は1日目、退院時サマリーの場面は、退院を決めていれば退院の日、それ以外はいまの日（`briefDay`）。**判定の語は使わない**（テストが検査する）。**誰の記録かを、送る前に確かめる**: 要約を付けて送るとき、記録の問題の名前と、いまの症例の一行を見せて「同じ患者のものですか」と確認する（記録と症例の組ごとに、このタブで1回。新しい会話で忘れる。キャンセルすると何も送らない）。年齢・性別が同じ別の患者の症例に打ち直しても記録の連動が続くため。

**書籍の根拠の持ち越し**（`web/case-record.js`）
- **記録の形**: `problems[].refs: [{ title, page, section?, via: "found", added }]`（1つの問題に8件まで。題名200字・頁40字・節100字）。先生が検索で残した頁だけを保存する。**採用した草案の引用**（問題・評価・計画の項目の `cites`）は、これまでどおり項目に付いたまま持ち越され、`refsOf(p)` が、残した頁と合わせて1頁1回で並べる（先生が残したものが先、`via`: `found`／`cited`、それぞれ加えた日つき）。Web の引用は書籍ではないので並べない
- **後日の頁は出さない**: `asOf(rec, N)` が、N 日より後に残した頁を除く（引用は、それを持つ項目が N 日までのものだけ）
- **画面**（`web/record-ui.js` の問題カード「書籍の根拠（どこを見たか）」）: 並べた頁（残した頁には「外す」。引用の頁は項目と一緒に消えるので外せない）、「書籍を引く」（**問題の名前だけ**で `/api/search`。識別情報らしき文字があれば送らない。名前は、いま記録にある文字を使う）、見つかった節（近い順に最大6件、節の冒頭を畳んで添える）、「この問題の根拠に残す」（題名・頁・節の名前だけを記録に入れる。同じ頁は2回入らず、引用の頁とも重ならない）。検索の結果は画面のメモリだけで、保存しない
- **退院時サマリー（A08）**: 主病名・副病名の各問題の下に「書籍の根拠（先生が残した頁・採用した草案の引用の頁です。この記載の内容を書籍が支える確認ではありません）」と頁を並べる（退院の日までの分）。**「出どころの印を残す」を外したコピーでは出ない**。入院時・経過・中間サマリーの記載には出さない
- 日付の変換（`relativizeRecord`）は、書籍の題名・節にはかけない（患者の日付ではない）。保存の入口の識別情報の検査は、これらの文字にもかかる

**画面**: 症例のバー（記録の連動のあるとき）の下の「草案の場面」（既定は共通の見出し）。記録を開いていない間は、記録の要る場面を選べない。選ぶと、見出しの説明と、渡すものが出る。場面は、会話を開き直しても、そのターンの「草案の場面」として残る。

**テスト**: `worker/test/scenes.test.ts`（双子・見出し・役割・プロンプト・HTTP・拒否・識別情報・保存しない）、`worker/test/brief.test.ts`（要約の中身・後日を含まない・空欄・日付・判定の語・大きさ・純関数）、`worker/test/refs.test.ts`（頁の形・残す／外す・後日・A08・印を外したコピー・保存・画面の固定）、`tests/e2e/ui_scene.py`（場面の選択・見出し・要約の表示と送信・識別情報・会話に要約が残らない・頁を引いて残す・A08・開き直し）。既存の固定を更新: 記載の組み立ては `draft-scenes.js` だけを新たに import する（`note.test.ts`）／記録の画面の通信先に、LLM を呼ばない `/api/search` を足した（`records.test.ts`。`/api/ask` は引き続き禁止）。

**実装中に直したこと**: 「書籍を引く」が、描画のあとに打ち直した問題名ではなく古い名前で検索していた（識別情報の検査も古い名前にかかっていた）→ 現在の記録の名前を使い、名前を打つとボタンが追従する。偽のモデル（devserver）が追加した規則の見出しを回答の見出しにしてしまっていた → 除外した。

**独立レビューを受けた修正（PR #17 のマージ後。2026-10-25）**: 別の目で「後日の事実・空欄・識別情報・別の患者・見出しの双子」を破れないかを調べさせ、再現できたものを直した（各項目は、まず失敗するテストを書いて確かめた）。
- **要約に入れた AI 草案の数値が、先生の入力扱いで数値の突き合わせを逃れた**（要約全体を「先生の入力」として渡していた）→ 「（AI草案を採用したもの）」の行を除いた分だけを先生の入力にする（`userBrief`。画面の印と Worker の印が同じ文字であることをテストが固定）
- **年齢・性別が同じ別の患者の症例に打ち直すと、前の患者の記録の要約が付いた**（記録の連動が続き、`isRecordCase` が通る）→ 送る前に、記録の問題の名前と症例の一行を見せて確認する（上）
- **問題の順序と主病名/副病名が日つきでなく、前の日の要約に後日の選びが出た**のに、先頭の行が「後日の事実は含みません」と言っていた → 言い直し、主病名/副病名は退院時サマリーの場面だけにした
- **救急以外の場面で採用して作った問題に〔救急から〕が付いた** → 採用した項目が、どの場面の草案から来たか（`scene`）を持ち、〔救急から〕は救急の場面（と、場面のない共通の草案。従来どおり）だけ
- **採用の取り下げが、先生が残した頁・確度・主病名・推移・課題つきの問題ごと、黙って消した** → 先生が手を入れた問題は残す
- **空の行（「＋ 計画を足す」だけ押した行）が、要約の行になり、名前のない問題ができた** → 文のない行は行にしない
- **中間サマリー・退院時サマリーの場面の指示が、要約に無い情報（転換点・推移の履歴）を指していた** → 要約に入れた（上）
- **入院時の場面が、今日の時点の記録を受け取った**（入院時の記載は1日目の時点）→ 1日目
- **重い記録で行の途中で切れ、何が落ちたか分からなかった** → 行ごとに外し、最後の1行に外した数を書く
- 小さいもの: `headingRole("constructor")` が関数を返した（`Object.hasOwn` で読む）／会話に保存する `payload.scene` を検査していなかった（6つの場面だけ）／「該当なし」の行に採用の印が付き、「該当なし」という問題を作れた（印を付けない）／記録が連動しなくなった直後に場面を送ると、黙って共通の見出しに戻った（理由を出す）
- **作業中に見つけた**: 症例を打ち直して固定し直すと、記録の連動中なのに、経過・中間・退院の場面が選べなくなり、選択も共通の見出しに戻った（先に選択肢を更新し、記録が新しい症例の版を覚えるのがあとだった。マージ済みのコードにもあった）→ 固定のあとにも更新する
- **直さなかった**: 参照した頁の題名・節に日付があっても残る（書籍の日付で、患者の日付ではない。意図どおり）／AI の項目を別の問題へ動かしたことが前の日の記載に反映される（8.14 からの限界のまま）

**限界・残り**
- **本物の API での、場面ごとの草案の書きぶりの確認は、まだない**（見出しの下の指示・「記録にない」と書かせる指示が守られるか、経過・退院の要約の質は、医師が数例見て決める）
- **場面・症候の答えの `ROUTES` による振り分けは、A04 と A01 を実装した**（8.18。A01 は 2026-10-25 に確定として扱った）。外来再診の記録と A02 の記載は 8.19 で実装した（**場面（AI の草案）はない**）。Modules との往復（段5として挙げていたもの）は、1f の決定で Casebook への接続（8.17）に替えた
- 場面の見出しと、役割の対応は作成者の案（8.5 の表から）。見出しを変えるときは、`SCENE_SECTIONS`・`draft-scenes.js`・テストの表を一緒に直す
- 要約に入るのは、先生が記録したものと、日ごとの文の4つだけ。問題名・評価・計画の文は、いまの文（履歴を持たない。8.14 の限界のまま）。要約は5000字までで、重い記録では、優先順位の低い問題が渡らない（画面に出る）
- 書籍の根拠は、**採用した引用**と**先生が残した頁**だけ。採用しなかった草案の頁、回答中の他の頁は残らない。A06・A07 の記載には出ない（A08 の診断ごとだけ）
- **更新したら、すべての端末で画面を開き直す**: 更新の前から開いたままの古い画面で記録を開いて保存すると、残した頁（`refs`）が消える（古い画面は知らない項目を保存しない。8.14 と同じ）
- 問題の名前が検索語になるので、名前が短い・略語だけだと、関係のない節が出る（先生が選ぶ。残さなければ何も残らない）。症例の値や年齢は、検索に入れていない

### 8.17 段5: Casebook へ送る（2026-10-25。医師の決定 `docs/clinical-use.md` の 1f）

**範囲**: 症例の記録から、clinical-casebook の**受け渡しパケット**（`CBH1:`。Casebook の `docs/contracts/handoff-packet.md`）を作り、クリップボードに載せる。**送る向きだけ**。Casebook から戻す向き、通信、新しい書き込みはない。あわせて、症例の年齢欄を**歳の整数**にした（決定 4。Casebook のパケットが年齢を歳で持つため）。

**全体の流れ**

```
記録（rec）──candidates(rec)──▶ 項目の候補（key・種類・日・出どころ・文・送れない理由）
                                   │ 先生が選ぶ（AI の草案は初め選ばれない）
        buildPacket(rec, 選び) ◀───┘   送り先: 新しい症例（年齢・性別・場面・実/架空を先生が選ぶ）／既存の症例（症例コード）
                 │ 形の検査（validatePacket）→ CBH1: + base64url + CRC-32
                 ▼
        クリップボード（と画面の欄）──先生が Casebook に貼る──▶ Casebook の確認画面で「取り込む」
                 ▲
        先生が「取り込みました」を押す → 送信済みの印（と症例コード）が記録に残る
```

**記録の項目 → パケットの項目**（`web/casebook-packet.js` の `candidates`。決定論。AI も書籍検索も使わない）

| 記録のもの | 種類 | 日 | 出どころ | 備考 |
|---|---|---|---|---|
| 救急の入力: 主訴と経過・バイタル・身体所見と検査 | `course` | 1 | user | 「主訴と経過: …」の形の文。数値は文のまま（検査項目には変換しない） |
| 救急の入力: 既往・内服・先生のアセスメント | `note` | 1 | user | 既往・内服は文のまま（背景 `history` の区分には割らない） |
| 問題 | `problem` | 加えた日 | AI の草案から採用した問題は ai | 印（`[推論]`・引用・〔AI草案〕）は外す |
| 診断 | `diagnosis` | 確度を選んだ日 | 問題と同じ | **確度が空欄なら作らない**。疑い・可能性が高い→`suspected`、確定→`confirmed`。除外は種類がなく、送れない |
| 評価・計画・推移・コール基準・入院時の欄 | `note` | 加えた日（推移はその日。**計画は先生がその状態を記録した日**） | 評価・計画は ai か user | 問題に属するものは `problemId`。**計画は状態を語にした文**（計画（予定・検討）／（実施の記録）／（変更）／（中止・しない）＋理由）。治療の開始・中止の項目にはしない |
| 日ごとの文 | `course` | その日 | user | 前回からのイベント・主観・所見の推移・全体・栄養活動・翌日の確認 |

**項目の ID と再送**: ID は、記録ごとの種 `seed`（英小文字 10 文字。乱数は画面が渡す）、項目の `key`、改訂番号から SHA-256 で決める（ULID の形）。**同じ項目は何度作っても同じ ID なので、Casebook に2つできない**（Casebook は同じ ID を上書きしない）。送信済みの印は `{ h: 内容のハッシュ, r: 改訂 }`。内容が変わった項目は「送信後に直した」で、**選ぶと改訂を1つ上げた新しい ID で送る**（Casebook にある前の項目は残る。Casebook は上書きしない仕様）。印は「取り込みました」を押したときだけ（コピーでは付けない。取り込まれなかった項目が「送信済み」として隠れないため）。

**状態**（`rec.casebook`。`web/casebook-state.js`）: `seed`・`code`（Casebook が示した症例コード。あれば次は追加）・`sent`（印。1000件まで）・`count`。日付・時刻は持たない。形は読み戻すときに検査する（種は英小文字だけ、症例コードは Casebook の形、印のキーは英数字と `.-`、**印のハッシュは英字 a〜p の 8 文字だけ**: サーバーの識別情報の検査〔8桁以上の数字の連続、「ID」「MRN」のあとの数字〕に当たる形が作れない）。

**止めるもの**（`web/casebook-guard.js`）: 識別情報らしき文字（画面と同じ `id-guard`）、暦日、電話、郵便番号、12桁以上の数字、メール、中身がない文。**文は先に Casebook と同じ形に畳む**（不可視文字を除く・全角を直す〔NFKC〕・ダッシュの類を「-」に・数字のそばの「ー」を「-」に）。日付の形は、年月日の各種の区切り、年月、月日（存在しない日も）、元号（漢字・英字の略記）、英語の月、漢数字、3つの数が日付として成り立つとき（24/10/2025、25.10.24。36.5/37.2/38.1 や 94 / 96 / 98 のような3回の測定値は日付にしない）。Casebook の `lintAnonymization` が error にするものを、この側が通さない: 手で挙げた形の一覧と、**乱数で作った 16 万通りの形**（全角・他のダッシュ・不可視文字の差し込みを含む）を Casebook 自身の関数と突き合わせた（`scripts/compare_casebook_guard.mjs`。Casebook の作業ツリーで動かす。`CASEBOOK_DIR` を渡した試験は手で挙げた一覧を毎回突き合わせる）。この側だけが止めるものがある（`カルテ番号 12345678`、小文字の元号、`500-1000 mL` のように Casebook も止めるものを含む）。氏名は、どちらも error にしない（Casebook は敬称つきを警告にする）。**検査は分ける前の文全体にかけ、止まる文の断片はどれも止める**。1つの文は 500 字まで: 超えるときは文の切れ目で番号つきに分ける。1回は 100 項目まで。

**送れない・送らないもの**: 外来（受診日の暦日が要る）、検査値・バイタルの項目（Casebook の検査項目名への対応表がなく、自由文からの数値の取り出しは取り違えの危険がある。契約も「数値を転記・要約する経路は作らない」）、病着からの経過分、課題・サマリー・退院時の薬・主病名／副病名、書籍の頁。画面にも書いてある。

**採らなかった案**
- 計画を `treatment` の開始にする: 「実施した」と読まれる。状態を語にしたメモにした
- コピーしたときに送信済みの印を付ける: 貼らなかった・取り込まれなかったときに、項目が「送信済み」の陰に隠れて失われる
- Casebook の受け渡し箱（IndexedDB）を使う: 別オリジンなので使えない。同じオリジンに載せ替える案は、保存先の境界を広げるので採らない
- RAG から Casebook へ通信で送る: 患者に由来する文書を外へ出す経路が増える。クリップボードなら、先生の操作だけで運ぶ
- 実症例／架空症例の既定を置く: 付け忘れると架空症例が実症例の一覧に混ざり、付けすぎると実症例が登録の候補から外れる。**毎回、先生が選ぶ**（既定なし）

**リスクと限界**
- **実症例を送ると、Casebook に実症例として入る**。入れ間違い（架空を実症例に）は集計に混ざる。画面に「取り込んだあとに変えられない」と書き、選ぶまで作れない形にした。作成者の案: 「架空症例を作る」から入れた症例は印をたどれるが、いまは持ち越していない（必要なら足す）
- クリップボードに、パケット（匿名化済みの文）が残る。貼ったあとに別の物をコピーすれば置き換わる
- 日の対応: RAG の「入院N日目」（救急で採用した項目は1日目）を、そのまま Casebook の病日にする。救急の翌日に入院した症例など、Casebook の入院日と食い違うときは、取り込んだあとに Casebook 側で直す
- 印は 1000 件まで（900 件を超えると、印のない項目は送れない理由を出す）。直して送り直せるのは 9 回まで（超えた項目は送れない理由を出す）。黙って印を落とさない
- **更新したら、すべての端末で画面を開き直す**: 更新の前から開いたままの古い画面で記録を保存すると、`casebook`（種・症例コード・印）が消える（古い画面は知らない項目を保存しない。8.14 と同じ）。種が変わると、送信済みの項目が別の ID で送られ、Casebook に重なる
- 本物の Casebook の画面での取り込みの確認は、まだない
- 年齢の整数化: 年代より個人に近い情報になる。モデルにも整数の年齢が渡り、会話・記録に残る。90歳以上は「90」でよいと案内した。古い「70代」は読めるが、送るときは歳の整数が要る

**試験**: `worker/test/casebook.test.ts`・`tests/vectors/casebook-handoff.json`（Casebook 自身の符号化・ULID の出力）・`tests/e2e/ui_casebook.py`。`CASEBOOK_DIR=<clinical-casebook の作業ツリー> node --test test/casebook.test.ts` で、Casebook 自身の `decodePacket` と匿名化の検査にも通す。

別の目で「識別情報・日付の漏れ、実症例と架空症例、再送、サーバーの保存の制約、Casebook の契約」を破れないかを調べさせ、再現できたものを直した（再現を確かめたうえで、新しい変更で）。
- **別の患者の記録を上書きしうる**（重い）: 最初のパケットの作成が、クリップボードの返事を待ってから、前に読んだ記録を丸ごと書き戻していた。返事が遅い間に別の記録を開くと、その記録が前の患者の内容で上書きされ、打っていた文も消えた → **種を作った瞬間に、いま開いている記録へ書き**（待つ前に）、返事のあとは、開いている記録・パケットが同じときだけ画面を直す。試験: 返事を 2.5 秒遅らせて別の記録を開く（旧い順序では3件失敗することを確かめた）

- **印のハッシュがサーバーの識別情報の検査に当たりうる**（約 1e-5 / 印。当たると、その記録は以後保存できない）: 36 進数のハッシュに「id0273」のような形ができた → 英字 a〜p の 8 文字だけにした

### 8.21 架空症例の模擬: 先生の行為に応じて進む症例(2026-10-26。医師の決定 `docs/clinical-use.md` の 1h)

**2回目の決定(2026-10-26。`docs/clinical-use.md` の 1h の2回目の表)で、下の要点の「1回だけ」「進行中は AI を呼ばない」は改めた**: 進行中にも AI が続きを書く(D4 c)。害のある行為の帰結まで書く(D3 c)。続きは、検査を通した構造の差分(新しい状態の事実・出来事・根拠の節)として設定に足し、**どの行為の後・どの境界に足したか**を持たせる。過去の記録を書き換えない(足した差分は、足した時点より後の再演にだけ効く)ので、同じ設定(続きを含む)と同じ行為の記録なら、同じ再演になる。以下は1回目の要点(段0〜1b の前提)。

**要点(1回目)**: 症例の「設定」(隠れた真の状態)は、AI が書籍を根拠に**1回だけ**書き、検査を通して凍結する。進行中は AI を呼ばない。決定論のエンジンが、「凍結した設定＋先生の行為の記録」から、答え・結果・状態の変化を再演する(同じ操作には同じ結果)。AI を使うのは、設定を書くときと、決定点の A/P の草案(採用は今の形)だけ。理由は、Modules の「LLM が患者として自由に話す形は採らない。症例にない事実を作る余地があるため。この点は変えない」(`clinical-modules/docs/training-automation.md` の 3.3)を守りつつ、筋の通った進行を作るため。

**設計の骨子**(案の全体は、先生への提案書。ここは実装の前提だけ)
- **設定の形**: JSON(配列だけ。構造化出力は開いたキーの辞書を書けないため)。`patient`・`opening`・`states`(s0 と、s0 からの差分の状態)・`orders`(行為と、返す結果の質問)・`moves`(状態の移り変わり。`if_done`／`if_not_done`、`at` は `next` か `enter:<段>`、`basis` は書籍の節)・`assumed`(設定の想定。「正解」と呼ばない)。
- **症例が返すのは生データだけ**。先生の読み(assessment・reason・none・action の質問と、呼び出し側が挙げた読みの質問)には値を持たせない。読みは先生が選ぶ。
- **検査**(`web/sim-case.js`。Worker の双子は段2): 背景(`ent: context`)は s0 のあと変えない／行為のあとにだけ意味のある値を s0 に置かない(オーダーの結果は除く)／時刻の質問の事実を持たない／診断名を導入・出来事・答えに出さない／評価の語・日付・用量・閾値・識別情報を拒否／すべての状態に届く・行為のない自然経過が必ずある／行為で分かれる遷移は書籍の節が必須／見える質問のすべてに値(どれが大事かを返事の違いで漏らさない)。
- **再演**(`web/sim-engine.js`): 行為は `ask`・`do`(`q=選択肢`)・`say`・`wait`・`stage`。**時間は境界(`wait`・`stage`)でだけ進む**。聞く・診る・測るは時間を使わない。結果は、オーダーの次の境界で、状態が動く前に返る。聞き直しは、いまの状態の値を新しい記録として返す(前の記録は書き換えない)。設定にない項目は「設定がありません(未確認。陰性ではありません)」。判断の質問・診断名・まだ明かしていない値には答えない。状態の id と設定の想定は `internal` にだけ置き、記録に出さない。
- **段**: スキルの救急の4段(初期評価・安定化 → 原因検索 → 再評価・Disposition → 締め括り)。段1b の画面は、段を表示して前へだけ進め(境界)、聞ける項目は段で絞らない(段で絞ると、何を聞くべきかの手がかりになるため。並びはフローの段のまま)。再評価の質問はフローでは原因検索と同じ段(p3)にあるので、段で絞るなら `cat` で分ける(段3で再考)。

**段1b の画面**(`web/sim-model.js` 純関数・`web/sim-ui.js`。救急の入口「架空症例の模擬（試作）」): 設定を貼る(検査を通したものだけ。救急のフローだけ。1区切りの分は表示だけ) → 状況(年齢・性別・時刻・段・導入) → 聞く・診る・測る(先生が聞いた・行った事実から見える項目だけ。結果はオーダーし、返ってから) → 行為の板(フローの action の質問。どの症例でも同じ一覧で、手がかりにならない。用量の欄なし) → 説明・相談・行き先(先生の言葉。識別情報は入れない) → 受け皿 → 先生が選ぶ項目(読み・判断・行き先) → 自分の A/P → 経時メモ(消さない) → A04(読み取り専用・コピーは見出しつき) → 振り返り。
- **読みと生データ**: RAG の `JUDGMENT_IDS`(抽出でモデルに見せない、先生の読みの質問)のうち、ベッドサイドで見えるもの(起立性変化・受動的下肢挙上・歩行時の SpO2 など10問。`SIM_RAW`)は、模擬では症例が返す生データとして扱う。作成者の案で、医師が入れ替えてよい。
- **聞ける項目**は、隠れた設定ではなく、先生が聞いた答え・届いた結果・自分の行為から決める(設定から決めると、どの項目に意味があるかを漏らす)。
- **受け皿**: 症例が言ったことは答えではない。先生が入れるまで記載に入らない。最初は何も選ばれていない。陰性・不明・評価不能・結果待ち(宣言 `br`)・時刻は1件ずつ。入力済みの答えは上書きしない(新しい値は「入力済み。上書きしません」と出し、片付けられる)。
- **記載**: A04 を `assemble` で決定論に。症例の入力は、年齢・性別・先生の答え・自分の A/P だけ(隠れた設定・想定・状態は入れない)。行為の時刻の質問が空なら、表示の時刻を入れる。
- **振り返り**: 確認のあとにだけ設定の想定を開く。鍵の所見(`assumed.key`)を「行き先を記録する前に聞いた／後に聞いた／聞かなかった」で並べるだけ(Modules の想起訓練の振り返りと同じ並べ方。点数・正誤・色なし)。
- **保存しない**: 設定・行為・答えはタブのメモリだけ。通信しない(フローの構造の静的ファイルを読むだけ)。ブラウザの保存領域にも置かない(e2e が保存領域への書き込みを1件も許さない)。
- **D7(依頼の印と F4 の除外)** は、模擬が依頼を送るようになる段2に回した(1b の画面は依頼を送らない)。

**段0・1a・1b の試験**: `worker/test/create.test.ts`(履歴・生成中の伏せ)、`worker/test/sim.test.ts`(検査の26の変異、再演、乱数の行為記録400本の性質、純関数であることの固定)、`tests/vectors/simcase.json`。再演の変異(結果の質問をいまの状態で答える・読みに答える・段を戻せる・出る時を問わず遷移する)で、試験が落ちることを確かめた。段1b は、画面の部品の試験(受け皿・上書きしない・行為の時刻・記載に隠れた設定が入らない・振り返り・import の固定)を `worker/test/sim.test.ts` に足し、`tests/e2e/ui_sim.py`(試験用の設定 `tests/e2e/sim_fixture.json` で、58項目。通信・保存領域を見張る)で画面を確かめた。

**限界**: 設定の生理の整合は機械では確かめきれない(段2以降は、振り返りで先生が印を付け、版を更新する)。本物の API・書籍での確認はない。段1a の設定と e2e の設定は試験用の仮のもので、訓練には使わない(1h の6)。いまは、先生が自分で設定の JSON を書くか、段2を待つしかなく、訓練にすぐ使える形ではない。
