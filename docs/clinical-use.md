**実装の順序（作成者の案）**: ① 会話の保存と、安全部品（数値の突き合わせ T1-6・引用のない文の薄い表示 C6）→ ② 症例の固定表示とアセスメント・プランの草案 → ③ カルテ記載の下書き → ④ 架空症例の作成。①は実装済み（PR #6。マージ済み）。②は実装済み（下の「症例モードの細目」）。③は実装済み（下の「カルテ記載の下書きの細目」）。④は別のPRで、設計を `docs/enhancement-plan.md` の 7 に置く。

**症例モードの細目（作成者の案。実装済み。変えたいときは言ってください）**

- 入口はヘッダーの「症例」。年代（10歳刻みの選択。乳児・幼児・学童は別の区分）・性別・場面（外来・救急・病棟）・主訴と経過・バイタル・身体所見と検査・既往と内服・先生自身のアセスメント（任意）。固定すると画面の上に1行で残り、質問のたびに自動で付く（「質問に付ける」で切れる）。症例は最後の質問にだけ付け、履歴には入れない（費用が伸びない）
- 4つの依頼（アセスメントとプラン（草案）／鑑別と反証／見落としチェック／コンサルト・医師コールの基準）は固定の見出しで出る。症例を付けた自由な質問も、同じ症例の前提で答える
- **識別情報のガードは、症例のすべての自由記述の欄にかかる**（入力中の警告、送信前の確認、サーバーの入口、保存の入口）。日付は経過で書く（2.1）。稀な組み合わせは一般化して入れる（2.2）
- 症例は、**会話の往復に付けて保存される**（`payload.case`。1d の①と同じ保存先・同じ期限・同じ削除）。ブラウザの保存領域には置かない。会話を開き直すと、その会話で最後に付けた症例が固定し直される。「新しい会話」は症例を外す（まだ質問していない症例は保存されていないので、確認を出す）。識別情報の確認を通した質問は、症例ごと保存しない
- 出力は草案: 画面に「草案・最終判断は医師」。コピーした先頭にも印が付く。書籍から書いた文は引用の印、引用のない文は `[推論]` `[標準・出典未確認]` `[施設依存]` のいずれかを付けさせる。薄い表示と数値の突き合わせは、そのまま効く（症例に入力した数値は突き合わせの対象外）
- **「先生の案との差」は、自分のアセスメントを入力したときだけ**。違いを並べるだけで、正誤・点数・評価は付けない
- プロンプトの書きぶりは、**本物の API でまだ確認していない**（開発環境に鍵がない）。マージ後の最初の数例で、医師が見出し・印・反証の書きぶりを見る

**カルテ記載の下書きの細目（作成者の案。実装済み。変えたいときは言ってください）**

- 入口は2つ。アセスメントとプラン（草案）の項目の「採用」→ 回答の下の「記載の下書きを作る」。固定した症例の横の「記載」（症例の入力だけで作る）。**採用は、アセスメントとプランの草案だけ**で、問題リスト・各問題の評価・初期プラン・コンサルト・医師コールの基準の項目（箇条・段落・表の行）に付く。草案自身についての節（確認すべき数値・書籍に見つからなかった点・先生の案との差）には付かない
- 型は、clinical-modules の記載の型から**欄の名前・順序・必須か条件つきか・版だけ**を取り込む（`scripts/import_note_types.py`。取り込んだコミットを `web/note-types.js` に記録）。最初の型は、救急外来初療（A04）・外来初診（A01）・病棟入院時（A05）・病棟の経過（A06）・退院時サマリ（A08）・コンサルト依頼（B02）・申し送り（B06）。症例の入力は1回の診察の事実なので、**A06・A08・B02・B06 は多くの欄が「（未入力）」になる**（作文で埋めない）。欄にどの入力が入るかの表は `docs/enhancement-plan.md` の 7.3
- 組み立ては決定論（AI を使わない）。入るのは、症例の入力と、医師が採用した項目だけ。採用していない項目は入らない。未入力の必須欄は「（未入力）」、条件つきで中身のない欄は出さない。**日付・患者ID・氏名は入力していないので空欄**（`［日付］［患者ID］［氏名］`）。先生が症例に書いた自分のアセスメントは、「先生のアセスメント（入力）」として、AI の印なしで入る
- 草案の計画は「予定・検討（実施の記録ではありません）」と明示し、実施済みの欄には入れない。採用した項目が、選んだ型に入る欄を持たないときは、画面に件数を出す（黙って捨てない）
- 採用した項目には「〔AI草案〕」の印と、出どころの印（`[推論]` など・書籍の頁・出典の一覧）が付く。コピーのとき、2つを別々に外せる（数値の【出典未確認・要確認】は常に残る）。実際のカルテに貼るのは先生で、貼る前に確認・修正する
- 画面は読み取り専用。**送信・保存・書き出し・印刷・共有はしない**（コピーだけ）。採用の選びはタブのメモリだけで、閉じると消える。Worker に記載の API はなく、D1 への書き込みも増えない

**会話の保存の細目（作成者の案。実装済み。変えたいときは言ってください）**

- 保存の単位は、1往復（質問・回答・引用の印・見つかった節・数値の突き合わせ）。完了した往復だけ。回答の途中で止まったもの（縮退）も、見えている範囲で保存する
- **識別情報の確認を通した質問は保存しない**（画面は送らず、サーバーも質問に識別情報らしき文字があれば保存を断る）
- 最後のやりとりから**30日**で自動的に消える（`CONVERSATION_RETENTION_DAYS`。仮の値。`"0"` で自分で消すまで残る）。「会話」の画面から、1件ずつ・すべて消せる
- 上限: 会話 200 件（超えたら最も古いものから）、1会話 100 往復
- ログには出さない。保存したものを読むのは、アクセストークンを持つ本人の画面だけ

## 2. 入力の約束の細目（作成者の案から始めたもの。1b のとおり実装済み）

決定 3 の「氏名・ID は入れない」を、画面とサーバーで守れる形に落とす案。

### 2.1 入れないもの

- 氏名、患者 ID・カルテ番号・診察券番号、生年月日、住所、電話番号、メールアドレス、保険証・マイナンバー、施設名・病棟名・担当者名
- **日付は絶対日付ではなく経過日数で書く**（「3日前から」「入院2日目」）。画面の文言で促すだけで、**ガードは日付を検出しない**（1b の 1。clinical-modules の識別情報の警告と同じ扱い）

### 2.2 稀な組み合わせ

年代・性別・稀な病名・地域・職業の組み合わせは、1 つずつは識別情報でなくても、特定につながりうる。稀な症例は、主要所見を一般化して聞く（例: 具体的な稀な病名を出さず、病態で聞く）。ここは機械では検出できないので、入力欄の近くの文言で促す。

### 2.3 ガード（画面とサーバーの両方）

- 画面: 送信前に検査し、見つかったら種類の名前を示して「直す／このまま送る」を選ばせる（入力は消さない）。clinical-modules の `web/id-guard.js` と同じ考え方
- サーバー: `/api/ask` と `/api/search` の入口でも同じ検査をし、見つかって承認の印がなければ送らずに 400 を返す。これは事故を防ぐ網で、悪意のある回避を防ぐものではない
- 網にかかるもの: 8桁以上の数字の並び、電話番号らしき並び、ID/MRN の後ろの数字、メールアドレス、「患者ID」「カルテ番号」「診察券」「生年月日」「患者氏名」「マイナンバー」「保険証」「電話番号」「郵便番号」「〒」の語
- **氏名は検出しない**（敬称つきの語も。1b の 1）。氏名は「患者さん」「奥さん」など普通の語と区別できず、誤検出が多い（clinical-modules の 2026-10-15 の判断と同じ）。検出できないことを前提に、2.2 と画面の文言で補う
- 実装: 画面 `web/id-guard.js`、サーバー `worker/src/idguard.ts`。2つの実装は `tests/vectors/idguard.json`（臨床の文面が通る例を含む35例）で縛る。サーバーが見るのは質問と、履歴のうちユーザーの発言だけ（モデルの回答は文献番号などを含むので見ない）。一度確かめて送った質問は、履歴として送り直すときも確認済みの印を引き継ぐ
- 網にかからなくても、識別情報を入れてよいことにはならない

### 2.4 保存の範囲（会話・評価の質問以外は保存しない）

- Worker は質問・回答を保存しない `[確認]`: DB の部品（`worker/src/db.ts`）は読み取り（`all`）だけで書き込み経路がなく、ログ出力は `search.ts` の `console.warn` 1か所（トークナイザが使えないときのエラー文。質問は出さない）だけ。会話は端末のメモリだけ（アクセストークンだけ端末に保存）
- Cloudflare 側のプラットフォームのログ設定は、リポジトリからは分からない `[未確認]`
- 質問や回答を保存する機能（履歴・お気に入りの本文・書き出し）を足すときは、実臨床由来の質問が含まれうるので、先に医師が決める。端末内のしおり（書籍と頁だけで、質問文は含めない）は、この制約に収まる案
- 例外（1c）: 評価の質問は D1 に置く。評価の結果は保存しない
- 例外（1d）: **会話（質問と回答）は D1 に保存する**。症例モードで付けた症例も、往復の一部として同じ表に入る（識別情報らしき文字があれば保存を断る）。識別情報の確認を通した質問は保存しない。30日で自動的に消え、画面から消せる。書き込みの一覧は `worker/test/conversations.test.ts` で固定している（`usage_daily`・`eval_questions`・`conversations`・`conv_turns` 以外への書き込みと、質問を出すログは、テストが落ちる）

### 2.5 外へ出る経路

質問 → Worker → Anthropic の API。Web 検索をオンにすると、モデルが作る検索語がさらに外の検索に出る。そのため、プロンプトに「**Web 検索の検索語には、症例固有の値（年齢・検査値）を入れず、一般化する**」を足す案。README には「API 経由のデータは既定では学習に使われません」とあるが、最新の規約・保持の設定は、医師が確認する。

### 2.6 画面の常時表示

全画面の上に「**参考情報・患者を特定する情報は入れない・最終判断は医師**」を出す。clinical-modules の帯（「訓練・データ収集用（架空症例のみ）」）とは別の文言にする。消すボタンは作らない。

### 2.7 回答の姿勢

- 出力は「論点・根拠・反証」。特定の患者への指示の形（「〜を投与せよ」）にしない。診療判断の代行はしない（現行のプロンプトにもある）
- **引用のない文は、見た目で区別する**（書籍の記述ではなく、モデルの推論や一般知識であることが分かるように）
- 数値は、書籍で確認できたものだけを無警告にする。確認できないものは強調する（決定論の突き合わせ。`docs/enhancement-plan.md` の T1-6）
- **患者固有の用量計算（体重あたりの量、mL/hr）はモデルにさせない**。式と必要な入力だけを示し、「要検算」と添える。現行のプロンプトは投与速度（mL/hr）まで具体化するよう求めている（`worker/src/prompt.ts` の「回答の型」）ので、直す対象
- 書籍間・ガイドライン間の食い違いは、版・年を示して並べる（現行どおり）
- 末尾に「**施設プロトコルは別途確認**」を添える（決定 4）

## 3. 医師の側で確認する事項（作成者には見えない `[未確認]`）

- 施設の規程: 外部サービス（Anthropic の API、Cloudflare）への質問の送信、私物端末の利用が許されるか。質問は 2 の範囲に抽象化するが、送信先のルールは施設ごとに違う
- Anthropic の API の保持・ログの設定、Cloudflare のログの設定
- 既定の専門（プロンプトは現在「腎臓内科を志す若手医師」向け。clinical-modules は救急外来）

## 4. 変えないもの

- 渡し先は本人だけ。他の人への共有・提供は、方針の変更として先に医師に確認する
- 書籍テキストと頁画像は著作物。D1 / R2 は自分専用の非公開リソースにし、リポジトリには入れない
- アクセスは Bearer トークン。Cloudflare Access を前段に置くこと（`docs/enhancement-plan.md` の T1-2 で、Worker 側の検証も足す案）
- 回答は検討の材料。診療判断・用量決定は、原本・添付文書・施設プロトコルで確認する

## 5. 施設プロトコルを入れる余地（未決）

決定 4 のとおり、いまは入れない。**入れる日が来たときに、先に決めること**を残す。

1. **許可・機密区分**: 院内の資料を、外部のサービス（Cloudflare）に置いてよいか。施設の規程を、医師が確認する
2. **種別と出どころ**: 書籍と混ざらないように、種別（`books.kind`）に `protocol`、チャンクの出どころ（`provenance`）に `institution` を足す。タグは `[施設]` を付ける。書籍の引用と、施設の運用の引用は、画面で別の色・別のラベルにする
3. **版の管理**: 施行日・改訂日・改訂者・有効期限を持つ。期限切れは検索結果に出すが、警告を付ける
4. **優先順位**: 施設プロトコルと、書籍・ガイドラインが食い違うとき、隠さず両方を並べる。どちらを採るかは、画面の裏で決めない
5. **リポジトリには入れない**: 施設の内部プロトコルは、clinical-modules の `CLAUDE.md` の「絶対に入れない」のとおり、リポジトリに入れない。入れるのは、本人の非公開の D1 だけ
6. **取り込みの手順**: 書籍と同じ取り込み（`ingest`）を使えるか、書式（`docs/FORMAT.md`）に表や分岐図をどう載せるかを、実物を見て決める
